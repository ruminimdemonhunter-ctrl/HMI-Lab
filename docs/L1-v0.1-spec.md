# HMI Research | Level 1 v0.1 Contract

Status: **implemented locally, candidate for validation in user's Debian QEMU VM**.

## Architecture invariant

User -> L3 (human intent, user-pattern memory) -> L2 (OS adaptation and
resource policy) -> L1 (bounded behavior memory and low-level decisions) ->
permitted hardware-oriented actions. Telemetry and outcomes flow upward.

- L1's executable engine stays fixed while its behavior memory can change.
- L1 is operational without L2/L3, with very slow local self-adaptation.
- L2 can propose updated **behavior memory**; only the L1 validation boundary
  activates it. L2 cannot change core code/safety limits through that channel.
- L3 is not yet implemented. No L2 daemon or real actuator is implemented.

## v0.1 measurable problem

Can a memory-parametrized, fixed-resource C engine consume Linux pressure
signals, make deterministic bounded decisions, reject dangerous policy
updates and slowly self-adjust its decision stability at minimal cost?

### Input

Every ~1 second by default: `cpu.some.avg10`, `memory.full.avg10`, and
`io.full.avg10`. Linux reports these as percentage **stall time**, not
utilization. The adapter converts percentage to fixed-point basis points.
Missing/invalid input returns HOLD immediately.

### Behavior memory

- policy schema version, strictly increasing generation
- threshold for each stall signal
- required consecutive confirmations
- L1-local extra confirmation steps (0..2)

The compiled C engine bounds allowed policy ranges. Actions are advice only.

### Decision function

Priority: memory protection > I/O deferral > CPU interactivity > hold.
Each action requires consecutive confirmations, with hysteresis to prevent
thrashing. Invalid sensor data clears the pending candidate and chooses HOLD.

### Self-adaptation

Every 600 valid decisions at most, adjust the local debounce increment by
one based on the number of confirmed recommendation switches in the window.
This is slow parameter adaptation (not a trained artificial neural network).
It changes behavior, but cannot change immutable policy bounds or executable
logic. The interval is based on sample count, not wall-clock; the caller
chooses the sampling rate.

### Safety envelope and known limitations

- No root permissions or actuator calls.
- No VM/hardware/Windows settings modified.
- `l1_apply_policy()` is a single-writer process-local API. Atomicity here
  means a synchronous swap inside one event loop, **not** cross-process
  synchronization or multiprocessor atomic lock-free access.
- No cryptographic policy authenticity; local file permissions are not yet a
  security boundary for a deployed L2.
- No crash-persistent self-learning yet; restarting restores local state.
- No proven performance advantage over conventional OS scheduling.
- Linux PSI is guest-system-wide telemetry; a future scoped controller should
  use relevant cgroup PSI and only control its own test cgroup.

## Criteria before Level 1 can control any resources

1. Reproducible workload harness inside the QEMU guest; repeat trials.
2. Evaluate static baseline policy, heuristic adaptation and proposed learned
   policy separately, with measured confidence and trade-offs.
3. Quantify end-to-end overhead including sampling, control, logging,
   persistence, and the cost of L2 policy preparation.
4. Define explicit exclusive ownership of a test cgroup, rollback/fallback,
   rate limits, and a human kill switch.
5. Test for oscillation, sensor failures, invalid L2 input, crashes,
   restarts, VM suspend/resume and recovery.
6. No global kernel, CPU firmware, physical thermal, or host resource changes.
