# HMI L1 R2.0 — Adaptive Machine-Perception Architecture

**Status: design only, awaiting independent review. No R2 executable code exists.**

**Frozen evaluation protocol:** docs/L1-r2.0-evaluation-plan.md (first branch commit 15ecd2ac052128e09a0e297be2b28a148fe50364). Base: released RC0 main at 9098ea858d183160818cbcf424ca1d7c0cb90460.

## 1. North Star and boundaries

The desired end-product is a machine that evolves into a useful individual companion through accumulated experiences. It is **living-like**, not claimed sentient, conscious or biologically alive.

Its three layers have different responsibilities and timescales:

- **L1 / machine reflex intelligence, fast and bounded:** local machine-condition observations, immutable safety advisories, compact operational expectations, trustworthy anomalies and quality status. Its learning is **about machine pressure**, not user personality.
- **L2 / environmental intelligence, future:** workflow and application context, safe orchestration, permissions, action rollback, investigation of L1 reports. L2 cannot rewrite compiled L1 authority or bypass limits.
- **L3 / cognitive and personal intelligence, future:** longer-term memories, owner preferences, initiative and interaction personality. L3 cannot directly write L1 policy or grant itself privileged OS access.

Optimizing OS resources is a bonus. A measurable **nonregression constraint** for responsiveness, stability, security and overhead is mandatory. L1 alone cannot validate the whole device's experience, and a synthetic experiment cannot prove it.

The old 208-byte shadow learner remains independently experimental and cannot change the protected reflex action. Initial R2 does not alter original L1Core, L1Shadow, the 72-byte V2 persisted state, compiled priority memory > I/O > CPU > HOLD, or any historical evaluator.

A new perception observation is a **copy**; its output must never be fed into l1_step_at(), accepted as a privileged L2 command, or cause a production policy mutation. Machine state reports are *observations*, not actual OS control instructions.

## 3. Observation semantics

Current permitted initial inputs:
- Validated monotonic timestamp (milliseconds); explicit freshness/validity.
- CPU PSI 'some avg10', memory PSI 'full avg10', I/O PSI 'full avg10', integer basis points 0..10000.
- Explicit unavailable/invalid status.
- Read-only cumulative PSI totals may be added only if separately preregistered before R2.1 implementation.

CPU PSI measures stalled runnable time, not utilization. High CPU pressure can coincide with useful activity. Even if a workload is normal for a machine, it is not necessarily healthy or acceptable to the user. **Learned normality may not suppress protection or concern.**

Do not acquire app/window/process names, personal content, serials, files, keystrokes, screenshots, microphones, cameras, credentials, private raw traces or Windows host telemetry in this research phase.

Initial candidate descriptive machine-condition states (final exact mapping must be frozen before R2.1 coding):
- UNKNOWN
- QUIET
- CPU_PRESSURE
- MEMORY_PRESSURE
- IO_PRESSURE
- MIXED_PRESSURE
- UNRELIABLE

These are descriptions of coarse telemetry, not diagnoses of system faults, evidence of causation or user workflow classification.

## 4. Reflex, descriptive state and novelty are different signals

**Reflex action**: only the existing core can return HOLD, PREFER_INTERACTIVE, DEFER_IO or PROTECT_MEMORY. Memory priority and fallback are immutable under R2.

**Descriptive state**: a read-only classification of the current normalized observation, with explicit ambiguity/unreliable handling. It does not use learned history in R2.1.

**Learned operational norm**: compact aggregate statistics of past *valid* pressure patterns, independently tracked per machine. It is uncertain in cold start, low support, after resets or during severe drift.

**Novelty candidate**: a bounded comparison between current conditions and sufficient learned norms; values UNKNOWN / EXPECTED / SUSPECTED. SUSPECTED means statistically unusual under this learned baseline, **not** imminent hardware failure or a reason to execute an OS action.

**Quality/evidence**: status and counts accompany each classification. Confidence should mean documented sample support or validated calibration, not arbitrary pseudo-probabilities.

An unavailable sensor, stale sample, backwards timestamp or corrupted perception state must force no personalized novelty claim, and cannot alter the protected core's original fallback logic.

## 5. Design direction for bounded operational memory

The eventual R2.2 implementation can use coarse per-channel quantized histograms or saturating, fixed-point/decayed summary statistics, with separate timestamps and supporting counts. Before implementation, freeze the exact struct schema, arithmetic, eligibility, drift/reset rules, independent persistence format and test identities.

Mandatory properties:
- <=512 bytes new perception state, excluding the unchanged 104-byte core and 208-byte shadow state.
- No heap allocation or unbounded loops for per-sample inference/adaptation.
- Deterministic byte-level result given identical starting memory and observation history.
- Reject impossible measurements, invalid ordering, counter decreases where relevant, overflow, saturating updates and timestamp gaps outside the frozen eligibility envelope.
- New model begins WARMING_UP and abstains from claims of personal normality until evidence is sufficient.
- Non-personal, aggregate-only history. No large embeddings, raw log persistence or identification token.
- Adapt slowly enough to resist poisoning from spikes, but recover eventually when conditions permanently shift; evaluate both competing failure modes.
- Changing, resetting, saving or corrupting the new model must never change protected core memory, policy generations, held-out fixtures or action history.
- If future persistence is approved, use a distinct versioned state file with safe atomic publication, bounded length and corruption recovery. CRC detects accidents, NOT malicious tampering/authentication; production trust remains unimplemented.

This is a research contract. No current measured superiority or persona learning is implied.

## 6. Two-machine individuality experiment

Start independent machines A and B with **exactly the same initial executable, configuration and perception memory**. Give A a deterministic, development-like pressure history and B a deterministic, creative-like pressure history.

Example expected *possibility* on the same later probe: a sustained CPU-pressure interval may be unsurprising to A and surprising to B. However:
- The difference must match independent, predeclared synthetic reference labels and outperform a fair fixed comparator.
- The same legacy core must return the same advisory action and exact core bytes for identical probe observations.
- A/B must both abstain on invalid/unreliable probes.
- Both must remain deterministic when receiving identical histories.
- In the separate regime-swap experiment, useful interpretation must change gradually as the environment changes.
- Distinct learned bytes alone do not constitute intelligent individuality.

Dataset families, support requirements, controlled splits, immutable seeds, fixed-baseline comparisons, performance limits and explicit NO_GO / UNDETERMINED rules are preregistered in the companion protocol. Generator source and exact SHA-256 split manifests must be frozen in a separately reviewed commit **before implementing adaptive R2.2**.

## 7. Future test-only L1→L2 machine-signal interface

No L2 implementation belongs in R2.0. A potential future R2.4 typed report would contain:

| Field | Meaning |
|---|---|
| schema_version | Versioned report grammar |
| sample_relative_ms | Bounded timestamp relative to a run |
| telemetry_quality | OK, WARMING_UP, STALE, INVALID or RESET |
| descriptive_state | One of the exact R2.1 state enums |
| novelty | UNKNOWN, EXPECTED or SUSPECTED |
| evidence_samples / support | Count and sufficiency for learned baseline |
| reason_code | Frozen enum, not an unbounded free-text explanation |
| reflex_action | Advisory action from existing l1_step_at |
| reflex_source | Must equal legacy_l1_step_at |
| END marker/checksum | Optional if security model and parser specify it first |

This is an **illustrative interface sketch**, NOT an existing canonical protocol, a production authenticated API, an executable command format or authorization to configure the OS. Freeze exact fields, ordering, byte size, type validation, error handling and trust model before R2.4. Fail closed on unsupported version and absent provenance; source audit alone does not authenticate L2.

## 8. Scientific and engineering gate philosophy

*Utility* is separate from *distinctiveness* and *safety*.

Future engineering gate:
- Byte-for-byte unchanged legacy L1Core transitions and all published advisory actions with perception enabled/disabled.
- Full historical normal / NDEBUG / sanitizer / replay / state / proposal / bounded resource suite; all original GO/NO_GO verdicts remain frozen.
- New code stays within 512 bytes of perceptual state, candidate incremental optimized CPU median <=1000 ns/sample, p95 <=5000 ns/sample, and whole added program optimized peak RSS <=8192 KiB, with reporting of environment, warm-up and all repetitions.
- Strict malformed-input corpus, side-effect audit, finite deterministic execution and 0 OS actuation/Windows host mutation.

Future utility gate:
- Independent synthetic A/B train-calibrate-held-out splits and shared probes, no leakage or post-outcome threshold tuning.
- Per-machine class-specific false positives, misses, recall, abstentions, independent event counts and drift-recovery analysis, not just a global metric.
- Fair strong fixed no-memory comparator evaluated at the same operating point; no worse false alerts or recall on either machine, strict improvement on a preregistered, sufficiently supported anomaly class.
- If evidence is sparse, mark INSUFFICIENT_SUPPORT; if ambiguous, mark UNDETERMINED; if worse, NO_GO. No target moving.

These are **future experimental budgets and decision rules**, not claims about existing results.

## 10. Deferred decisions and permissions

Before coding R2.1: resolve precise state mapping and ambiguous overlap semantics in a separate frozen specification. Before coding R2.2: freeze memory fields, update math, corpus-generator SHA-256 and fixture identities. Before coding R2.4: freeze informational schema and authentication/threat assumptions.

NO R2 phase automatically authorizes a research-length real PSI recording, pressure generation, guest or host OS actuation, production L2 link, hardware modification or real user profiling. A real guest PSI recording requires a new user request specifying finite duration and exact guest-local destination. The separately gated V1.2 causal resource-benefit experiment remains BLOCKED and unrelated to the new primary HMI goal.

R2.0 is successful if it provides a clear, independently reviewable contract for experience-grounded low-level awareness *without making the machine less safe*. It cannot yet make a laptop individually intelligent.
