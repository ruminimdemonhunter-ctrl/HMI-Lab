# HMI Level 1 v0.4 frozen adaptive-evaluation protocol

Status: **frozen before implementation and before any held-out execution**.
Issue: [#3](https://github.com/ruminimdemonhunter-ctrl/HMI-Lab/issues/3).

Any change to held-out seeds, scenario rules, candidate space, loss, tie-breaks,
metrics, or guardrails after the protocol commit invalidates the held-out result
and requires a new preregistered evaluation version. Compile fixes that do not
change generated traces or scoring must be identified in the final report.

## Research question and candidates

On deterministic synthetic scenarios not used for parameter selection, does
the existing bounded `debounce_extra` adaptation improve labeled decision
stability relative to both the compiled default and a strong fixed policy?
Null and negative results are valid.

Every candidate calls the real `l1_step_at()` once per identical observation
and timestamp. No evaluator may duplicate the priority, threshold, hysteresis,
confirmation, invalid-input, or adaptation decision logic.

1. **Frozen default**: compiled default policy; adaptation disabled.
2. **Tuned fixed**: best policy selected only on training scenarios; adaptation
   disabled.
3. **Bounded adaptive**: the same training-selected policy; existing adaptation
   enabled with the unchanged `0..2`, 600-valid-sample, 600,000-ms limits.

A compiled boolean evaluation control may disable adaptation without changing
other decision behavior. Production initialization remains adaptation-enabled.
The flag is not policy-file writable, persisted, or exposed as a remote update.

## Determinism and independent truth

The generator uses PCG-XSH-RR 32 (`pcg32`) with 64-bit state and stream. Each
scenario derives independent truth and observation-noise streams from its base
seed and family identifier using SplitMix64. Integer arithmetic, inclusive
bounds, clamping, and PCG initialization are normative in the committed source.
No platform random source, wall clock, live PSI, or held-out feedback is used.

Latent CPU, memory, and I/O event flags form the oracle independently of noisy
observations. Oracle priority is the compiled priority: memory > I/O > CPU >
`HOLD`. Metrics treat each contiguous oracle-visible non-`HOLD` segment as one
event. Lower-priority latent events masked by a higher-priority event are not
separate detection opportunities until they become oracle-visible.

Nominal observations before noise are:

| Latent state | CPU some bp | Memory full bp | I/O full bp |
|---|---:|---:|---:|
| inactive baseline | 600 | 10 | 50 |
| CPU event | 3,600 | unchanged | unchanged |
| memory event | unchanged | 180 | unchanged |
| I/O event | unchanged | unchanged | 750 |

Independent uniform integer noise is CPU `[-400,+400]`, memory `[-40,+40]`,
and I/O `[-150,+150]`, then values clamp to `0..10000`. Family-specific false
spikes, threshold oscillation, regime offsets, invalid flags, and timestamps are
applied exactly as specified in the generator source. Truth never derives from
the resulting observation.

## Scenario families

Each split contains every family. Length is in samples; nominal regular cadence
is 1,000 ms. Truth start/duration jitter comes only from the truth PRNG and is
bounded in source so events remain inside the scenario.

| ID | Family | Samples | Required behavior |
|---:|---|---:|---|
| 0 | idle | 300 | no latent event; ordinary sensor noise |
| 1 | short-false-spikes | 450 | 1-4 sample threshold-crossing spikes; truth remains `HOLD` |
| 2 | sustained-cpu | 900 | three sustained CPU events with quiet gaps |
| 3 | sustained-memory | 900 | three sustained memory events with quiet gaps |
| 4 | sustained-io | 900 | three sustained I/O events with quiet gaps |
| 5 | overlapping-events | 1,200 | CPU/I/O/memory overlap and priority handoffs |
| 6 | threshold-oscillation | 1,800 | repeated near-threshold bursts plus visible events; can adapt |
| 7 | changing-regime | 1,800 | three baseline/noise regimes plus visible events; can adapt |
| 8 | invalid-data | 1,200 | invalid blocks during quiet and event periods |
| 9 | irregular-regressing-time | 1,200 | increments from 250/500/1000/1750/2500 ms and two 5,000-ms regressions |

Families 0 and 1 cannot reach either adaptation gate. Families 6 and 7 are long
enough to exercise it. Other families test that time alone or samples alone do
not authorize an update.

## Frozen split and seeds

For each base seed, all ten family scenarios are generated; the family ID is
mixed into both independent PRNG streams.

- Development seeds (generator/unit debugging only): `41, 43` (20 scenarios).
- Training seeds (parameter selection): `101, 211, 307, 401` (40 scenarios).
- Held-out seeds (one final evaluation): `1009, 2003, 3001, 4001, 5003`
  (50 scenarios).

Development data may debug invariants but may not select a policy. Training may
select the tuned policy. Held-out scenarios may not change code, parameters,
weights, aggregation, or prose interpretation thresholds. A held-out execution
begins only after this document exists in a pushed commit.

## Frozen training search

The Cartesian search contains 108 policies, all inside the compiled envelope:

- CPU trigger: `{2000, 3000, 4000}` bp
- memory trigger: `{50, 100, 200}` bp
- I/O trigger: `{300, 500, 800}` bp
- confirmation samples: `{2, 3, 4, 5}`

Generation is 1 and schema is 1. Each candidate is fixed (adaptation disabled)
and scored by micro-summed training loss over all 40 training scenarios.

Primary loss is stored in exact quarter-points:

`loss = FP*1 + missed_CPU*4 + missed_IO*6 + missed_memory*10 + switches*0.25`

A wrong non-`HOLD` action during an event is one missed sample for the oracle
class, not an additional false positive. A false positive is any non-`HOLD`
action while oracle truth is `HOLD`. Every action change, including to/from
`HOLD`, is a switch.

Tie-break order is: lower total memory-missed samples, lower memory-undetected
events, lower I/O-missed samples, lower I/O-undetected events, lower CPU-missed
samples, lower CPU-undetected events, fewer false positives, fewer switches,
then lexicographically lower `(confirmation, CPU trigger, memory trigger,
I/O trigger)`. The selected policy is written once as a normal strict policy
file and is the only non-default policy accepted by held-out mode.

## Frozen metrics and aggregation

For each controller, report each family and the aggregate:

- scenario count and sample count;
- primary loss plus scenario-loss minimum, median, and maximum;
- false-positive samples;
- missed CPU, I/O, and memory response samples;
- visible CPU, I/O, and memory event counts and never-detected counts;
- detection delay mean, nearest-rank p95, and maximum in sample intervals;
- action switches;
- adaptation update count and observed `debounce_extra` minimum/maximum;
- invalid observations and timestamp regressions;
- safety-fallback violations (non-`HOLD` on invalid/regressing input);
- `sizeof(L1Core)`, process peak RSS, and process CPU ns/decision.

Detection delay is `first matching sample index - visible-event start index`.
An event never matched before its visible segment ends is undetected and has no
finite delay; it remains separately counted. Aggregate values are micro-sums;
scenario loss distributions use one value per whole scenario. No confidence
interval is planned, so correlated samples will not be bootstrapped.

CPU measurement excludes trace generation. Held-out traces are generated once,
then controller/scoring passes repeat 100 times in Debian (first pass supplies
metrics). Controller order rotates by repetition. CI uses one bounded repetition.
RSS is the evaluator process-wide `ru_maxrss`, not attributable per controller.

## Independent safety guardrails and go/no-go

These do not alter primary loss or selection:

1. All candidates must remain within the compiled policy envelope and
   `debounce_extra` must remain `0..2`.
2. Invalid observations and regressing timestamps must produce `HOLD`; any
   violation fails the evaluator and CI.
3. On held-out data, adaptive memory-event recall must not fall below either
   baseline, adaptive memory undetected-event count must not exceed either
   baseline, and adaptive memory maximum detection delay must not exceed the
   tuned fixed controller. Any failure is an explicit memory-safety regression.
4. I/O recall, undetected events, and delay are reported independently as the
   second-priority safety result; any regression is unfavorable even if total
   weighted loss improves.

If guardrail 3 fails, or the tuned fixed controller outperforms adaptive on the
primary held-out loss, the conclusion is **no-go for resource-actuation work**.
Further simulation/core research may continue. Passing is not authorization for
actuation and not evidence of real workload optimization.

## Reproducibility and execution protocol

The evaluator lives in `src/level1/evaluation/`, uses C11/POSIX plus optional
Python 3 standard-library reporting, and writes only explicitly named test
artifacts. Planned commands from Debian are:

```bash
cd /home/lab/hmi/src/level1
make clean all test test-ndebug
ASAN_OPTIONS=detect_leaks=1 UBSAN_OPTIONS=halt_on_error=1 make sanitize
make evaluation-ci
make evaluation-train EVAL_POLICY=/tmp/l1-v04-tuned.policy
make evaluation-heldout EVAL_POLICY=/tmp/l1-v04-tuned.policy EVAL_REPETITIONS=100
```

Training output records candidate count, selected parameters, loss, split seeds,
and a deterministic trace checksum. Held-out output records the supplied policy,
seeds, checksum, all metrics, environment, compiler, command, and exit status.
The final report copies exact output; generated `/tmp` artifacts are not Git
inputs. GitHub Actions runs development/training and a one-repetition held-out
regression only after this frozen protocol is committed; Debian supplies the
reported 100-repetition CPU measurement.

The entire evaluation is read-only with respect to resources. It adds no L2/L3,
remote update path, scheduler/cgroup control, kernel/device access, or hardware
write. Simulation results must be described as heuristic evidence only.
