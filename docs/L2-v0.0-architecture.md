## 1. The actual mission

**Two initially identical operating systems should be able to develop measurably useful, different environments from their different histories.**

Example: a computer primarily used for software development might learn that code editing, build/test and documentation are commonly related. Another used for digital art might learn that canvas work, references, asset sets and exports belong together. These are **illustrative work patterns, not hard-coded professions, role labels or stereotypes**. One person can have many environments, and both devices should adapt when habits change.

The system should ultimately help with workspace layouts, project structures, virtual collections, tool grouping, resumable routines, navigation, unobtrusive suggestions and (much later) authorized system performance adaptations. **It must not silently move folders, infer identity, spy on content, or claim competence because two memory blobs differ.**

Operational individuality is a **bounded, explainable local history** which leads to *appropriate*, more useful outputs on the same request while conserving safety. That is a scientific hypothesis to test, not an achieved HMI milestone.

## 2. L1 / L2 / L3 responsibility and non-authority

| Layer | Job | Immutable boundary |
|---|---|---|
| **L1 — Machine reflex** | Protected CPU/memory/I/O condition decisions; R2.1 descriptors; bounded R2.2 pressure aggregates | Existing 104B core, 208B shadow, 72B V2 policy state, 112B R2.2 memory and old scientific outcomes never modified by L2 |
| **L2 — Adaptive Environment Engine** | Recognize *coarse context*, form workspace/routine relations, retain bounded operational identity, propose reversible changes and learn from explicit outcome feedback | No L1 policy writes, kernel/scheduler/privileged writes, filesystem changes or action execution in V0.0/V0.1 |
| **L3 — Future personal intelligence** | Interpret explicit user goals, long-term preferences, collaborative plans and initiative, only with separate consent | Cannot bypass safety/consent, overwrite L1 logic, infer approval from a model output or secretly collect user data |

L2 evolves **how the OS is used**; L3 may eventually understand **why the person wants to use it**. Neither PSI nor a coarse activity enum can recover the user's occupation, intention or creative content.

## 3. The six L2 modules

### A. Explicit Observation Gate — WHAT was permitted to be observed?
- V0.0: architecture only. V0.1: versioned, **synthetic-only** finite event streams. No real process enumeration, file scanning, keyboard, mouse, window titles, app/package listing, screen recording, network payload or PSI capture.
- Event fields: protocol version; simulated device key A/B; monotonically increasing time/sequence; provenance=SIMULATED; quality; coarse workspace handle; activity/tool-role enum; resource descriptor enum; explicit simulated outcome/feedback. No actual path, username, PID, command, file name or content.
- Later opt-in observation must be tightly scoped: explain category, purpose, retention, permission, on/off switch and revocation. Consent for workspace structure does not imply consent for file contents.

### B. Context Interpreter — WHAT is the OS situation?
- States: UNKNOWN, IDLE, FOCUSED, MULTI_TASK, BACKGROUND_BUSY, RESOURCE_CONSTRAINED, TRANSITION.
- Reason-coded deterministic combination of activity hints, session events and separately sourced L1 descriptive conditions.
- Missing source, invalid enum, stale input, out-of-order timestamp, reset, contradictory events => UNKNOWN/TRANSITION; no invented confidence or hidden activity inference.
- Context can change quickly. This is **short-term** and should not instantly rewrite long-term identity.

### C. Workspace Relationship Graph — WHAT tends to belong together?
- Bounded *local structural memory* of opaque workspace handles, type-only project/template nodes and tool-role categories, plus weighted association edges. Labels like CODE_EDIT / BUILD_TEST / DOC_VIEW / CANVAS / REFERENCES / ASSET_GROUP / EXPORT are **simulated functional categories**, not sensed occupation.
- Track co-occurrence and sequences only from eligible, appropriately sourced events; counters saturate and old edges decay deterministically; no unbounded dictionary, embedding model or database required in the first version.
- Graph allows multiple modes on one machine; no single immutable "programmer" or "artist" profile, and no forcing all behavior into one most-frequent workflow.
- In V0.1 this is a tiny in-memory graph from synthetic inputs. No user filesystem path or actual folder tree is scanned or retained.

### D. Routine and Continuity Memory — WHAT typically comes next?
- Track bounded, adjacent event-category transitions and resumable *session-level summaries*, with provenance and evidence count. Do not store keystrokes, window text or lists of files.
- Distinguish a one-off event from recurring routine using bounded support/hysteresis; cap learning speed and permit routine change, aging, reset and ambiguity.
- Memory evolves **slowly**; short-lived context and slow operational identity have different update gates. Do not reuse R2.2's 256-sample/4-window rule: that is L1-specific and does not model workflow evidence.

### E. Adaptation Planner — WHAT might help?
- Generates **typed, text-only proposals**, never executable strings. Potential kinds: WORKSPACE_LAYOUT_HINT, VIRTUAL_PROJECT_TEMPLATE, COLLECTION_LINK_HINT, SHORTCUT_GROUP_HINT, RESUME_FLOW_HINT and later NONCRITICAL_BACKGROUND_SCHEDULE_HINT.
- Each output includes proposed change, basis of synthetic evidence, alternatives, confidence-as-evidence-bucket (not fabricated probability), scope, risk, expiry, expected usefulness **hypothesis**, reversibility, required explicit user approval and abstain reason.
- A risk/permission filter can return NONE, ASK_USER or BLOCKED. It cannot return EXECUTED, cannot write to L1, cannot call a shell or filesystem API.
- Different machine histories may produce different proposals for an identical neutral prompt, **only when training evidence supports them**. Their appropriateness must later be evaluated independently.

### F. Outcome and Reversal Ledger — DID the proposal help?
- Future stages record explicit accept/reject/undo and **measured** interaction effort, without inferring feedback from silence or manufactured synthetic labels.
- A slow update increases/decreases a proposal preference only after verified feedback; negative signals, reversals and regime changes should constrain repetition.
- No persistent user telemetry in V0.1. The first proof uses simulated acceptance/undo events; real consent and benefit are separate future gates.

## 4. Interaction flow (conceptual, not executable)

```text
   simulated permitted events        protected L1 descriptive state
               |                         (read-only copy)
          provenance gate                    |
               +-------------+---------------+
                             |
                    fast context engine
                             |
                bounded relationship graph
                 + routine history ledger
                             |
                  slow operational identity
                             |
                  evidence-based proposals
                             |
                   permissions / risk gate
                             |
                     NONE / ASK_USER
                           / BLOCKED
                             |
                 offline synthetic report
                    (NO EXECUTOR)
```

The core distinction: **fast context is not slow identity**. A single evening of drawing must not erase a development workflow. A user spending months in a newly preferred mode must be able to shift the environment gradually.

## 5. Example: two evolving computers, no hard-coded career profiles

- Both virtual machines begin with **byte-identical empty L2 state**, same L1 safety snapshot and same candidate proposal catalogue.
- History A uses synthetic sessions repeatedly containing WORKSPACE_ENTER -> CODE_EDIT -> BUILD_TEST -> DOC_VIEW, with occasional CANVAS.
- History B uses synthetic sessions repeatedly containing WORKSPACE_ENTER -> REFERENCES -> CANVAS -> ASSET_GROUP -> EXPORT, with occasional CODE_EDIT.
- Neither stream exposes `programmer` or `artist` as an input field; the implementation does not use those labels.
- After support is established, identical synthetic query `PROPOSE_WORKSPACE_START` should produce **potentially distinct** ranked text-only environment layouts/virtual templates with visible evidence counts.
- Both machines must answer identically on malformed input, permission denial, safety conflicts and missing-support cases. Different outputs alone **do not** prove those suggestions are correct.
- A third machine with mixed histories must remain capable of presenting multiple modes rather than confidently assigning one profession; cold starts abstain.

Ground truth for proposal suitability must be frozen **independently** from the planner and scored against competitive fixed baselines on independent episodes. No utility GO from a generated fixture engineered to favor the scorer.

## 6. Folder evolution without destructive edits

The long-term request includes folder structure and workspace evolution. A **physical filesystem** contains fragile dependencies: build paths, resource links, creative-application project references, symlinks, permissions, VCS state and sync rules.

Therefore the order must be:
1. **V0.1–V0.3: recommend virtual organization only**, using synthetic opaque handles and text descriptions. No file operations.
2. **Later permissioned virtual workspace overlay** on a bounded opt-in guest test directory: collections, logical links, layouts/templates. Show a preview and reversible local mapping; never move actual files.
3. **Later still, separate authorization for physical guest operations**, with exact scope, preview, collision/symlink checks, durable rollback manifest, confirmed backups and independent tests. Never touch Windows-host directories. Silence is not approval.

This is *adaptive structure*, not automatic renaming/reorganizing of private folders.

## 7. Minimal architecture and resource constraints

V0.1 should be small enough to reason about completely: strict C11 pure core, fixed-width enums, caller-owned state, no per-event heap, deterministic saturating arithmetic, fixed-size arrays, stateless I/O adapter, no network or ML runtime. Proposed bounds to **freeze precisely in V0.1 before implementation**:
- Model state <= **8 KiB** including all graph nodes/edges/routine counters; no disk persistence.
- Whole offline analyzer <= **8 MiB RSS** in isolated Debian QEMU on finite synthetic fixture playback.
- Median CPU <= **50 microseconds per event**; individually timed p95 <= **250 microseconds** (initial prospective targets; not yet measured).
- Finite replay >=100,000 synthetic events; no unbounded paths/strings/log output.
- Start with at most 16 opaque nodes, 32 association edges and 16 routine-transition counters, subject to exact prospective V0.1 spec, never let these grow silently.

A 112-byte L1 pressure histogram is not a useful substitute for L2's **relations, workflow continuity, feedback**. L2 will not use an unbounded note store, call an external memory service or require cloud inference at this stage.

## 8. Roadmap — build individuality from the beginning, not after classification

| Milestone | Required deliverable | Evidence/authority |
|---|---|---|
| **L2 V0.0** — this draft | Redesigned OS identity architecture and test strategy | Docs only, pending human design review |
| **L2 V0.1** — First runnable proof | Synthetic-only event parser + fast context + **tiny evolving relationship/routine memory**; deterministic explanation of two distinct histories | Engineering integrity and state divergence only; no OS writes |
| **L2 V0.2** — Usable memory | Multi-mode identity, forgetting, regime changes, negative outcomes and bounded restart semantics on synthetic cases | Independent comparison to strong fixed-memory-free baseline |
| **L2 V0.3** — Safe proposal engine | Ranked **text-only** workspace/virtual-folder template suggestions; risk/approval gate | Synthetic independent suitability and false-intrusion metrics; no executor |
| **L2 V0.4** — Outcome feedback | Rejection/acceptance/undo reasoning and verified proposal usefulness in controlled synthetic experiments | Evidence of benefit vs fixed methods, not real-world transfer |
| **L2 V0.5** — Opt-in guest feasibility | Separately approved finite coarse local metadata observation; privacy revocation tests | No OS actuation or Windows host access |
| **L2 V0.6+** — Virtual adaptation | User-approved reversible guest sandbox *virtual* workspace organization; physical operations deferred further | New capability/rollback security reviews and owner authorization |
| **L3 future** | Higher-level explicit user goals/initiative | Never direct L1 write or implied consent |

L2 V0.1 should *not* be a generic idle/busy classifier plus a renamed memory counter. It must contain a demonstrable bounded **experience structure** from the first implementation. This is the correction to the earlier V0.0 draft.

## 9. Fail-closed safety and scientific honesty

- All original L1 protected source/state/history and RC0 tests remain unchanged. R2.3/R2.3b studies remain INVALID, R2.3c preflight PASS; R2 utility and individuality are UNDETERMINED.
- No user profiling or passive OS monitoring in V0.0/V0.1; any future data category requires explicit consent. No background service, actual folder access, process observation, real PSI, privileged command, scheduler/cgroup write, network call, or host modifications.
- Any model/graph output is a **hypothesis**. No machine individuality GO without independent context-conditioned suitability labels, safety-equivalent opposing controls and performance against strong baselines.
- A low-memory fixed C core can still be valuable: L2 should not claim to think like a human, self-modify executable code, acquire unrestricted autonomy or guarantee resource savings.
- Future real OS actions require a separated capability broker and **separate explicit approval**. No L2 proposal is a permission token.
