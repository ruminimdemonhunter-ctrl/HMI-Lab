# HMI L2 V0.0 — Architecture blueprint for individualized, permissioned OS context

**DESIGN ONLY. NO L2 EXECUTABLE, LIVE OBSERVATION, OS ACTUATION OR PRODUCTION AUTHORIZATION.**

- Issue [#33](https://github.com/ruminimdemonhunter-ctrl/HMI-Lab/issues/33); feature branch `feature/l2-v0.0-architecture`.
- Baseline: accepted L1 R2.3c merged into `main` at `74e2bd3d05cebc941742c5a67c545172a5b6b5c3`.
- Historical invalid R2.3 / R2.3b remain [PR #28](https://github.com/ruminimdemonhunter-ctrl/HMI-Lab/pull/28) and [PR #30](https://github.com/ruminimdemonhunter-ctrl/HMI-Lab/pull/30), neither merged; scientific `R2_UTILITY` / `R2_INDIVIDUALITY` remain UNDETERMINED. Do not rewrite these findings.

## 1. End goal: a device that becomes meaningfully different through experience

HMI's long-term vision is a **coherent machine intelligence stack** that can develop machine-specific expectations and, much later, safely adapt to individual use. L2 is not a rebranding of PSI metrics, a process priority daemon, a general purpose LLM in the kernel, or a personality layer. It is the **local OS-context reasoning tier** that starts to understand *what kind of operating situation the computer is in*, what changed, what available evidence supports the interpretation, and whether a possible adaptation is worth suggesting.

Meaningful individuality is an eventual demonstrated ability to make a **contextually appropriate different recommendation for two devices that have different justified histories**, while avoiding harmful differences on common safety situations. Different learned bytes or decisions alone are not sufficient. L2 may have hypotheses and explicit uncertainty; it cannot infer a user's intention, job, emotions, identity or task from PSI alone.

The three-layer boundary:

| Layer | Responsibility | What it may not claim/do |
|---|---|---|
| L1 — Protected reflex/perception | Constant-bounded machine-pressure observation and protected priority/advisory safety behaviors | No learner-to-action coupling; historic adaptation/prediction NO_GO; no proven benefit |
| L2 — OS context (this track) | Derive episodes, coarse resource context, continuity, explainable **proposals**, and a bounded device-local context summary | No kernel replacement, privileged write, L1 source edit, speculative app/user inference or autonomous OS changes |
| L3 — Future personal layer | Higher-level explicit user goals, memory, task narratives and initiative after separate authorization | Cannot bypass OS safety, directly edit L1 core, or create unconsented personal data collection |

Any possible future L2-to-L1 proposal must enter a **separately authorized**, validated, rollback-capable policy boundary; the current L1 core never accepts direct commands from L2. Lower-level safety and conventional OS policy always override higher-level desires.

## 2. Threat / authority boundary

**Windows host** is the development source and VS Code/Codex side of the lab. No executable generated here runs on or changes Windows services, settings, registry, disk layout, scheduler, sensors, devices, startup, firewall or protected paths. QEMU is the isolated Debian guest with no host filesystem mounts/raw physical device passthrough and normally restricted outbound network. The source sync remains one-way Windows -> guest, through loopback SSH; VM backups remain offline.

**L2 V0.0** changes docs only. Future **L2 V0.1** may run an *explicitly invoked, unprivileged, finite offline CLI* in the Debian guest on **synthetic fixture inputs**. It has no process enumeration, PSI capture, filesystem surveillance, packet observation, systemd unit, background loop, auto-start, network socket, privileged shell, kernel/cgroup/scheduler interface or live user data source. The CLI cannot issue commands to L1 or persist production user context.

A distinct, future user-authorized **guest observation** phase may read a fixed, coarse allowlist of OS signals with a named purpose, duration and privacy policy. Even that does not authorize actuation. A future **OS actuation** phase is a new separately approved research experiment requiring privilege separation, reversible allowlisted commands, verified rollback and physical/device safeguards. **No action executor interface is present in V0.0/V0.1.**

## 3. Architectural principle: Perceive -> Understand -> Remember -> Propose -> Verify -> (future, permissioned) Act

```text
                 PROTECTED L1 (unchanged)           SYNTHETIC OS EVENT STREAM
                     R2.1 descriptive               V0.1 OFFLINE ONLY
                    machine conditions                     |
                             |                               |
                    versioned read-only                  schema/quality
                    descriptor adapter                   validation
                             |                               |
                             +-------------+-----------------+
                                           |
                                  event gate / freshness
                                    + provenance label
                                           |
                                  finite context episode
                                   state machine (L2)
                                           |
                            bounded context summary/history
                            (no raw identifying traces)
                                           |
                                   proposal generator
                              explanation + alternatives
                                           |
                                 hard rules and risk gate
                          output=NONE / ASK_USER / BLOCKED
                                           |
                                 offline JSON/text report
                                           |
                            FUTURE HUMAN AUTHORIZATION BOUNDARY
                             (NO EXECUTOR EXISTS IN V0.0/V0.1)
```

L1 and OS event streams are **independent evidence**. L2 must identify provenance/quality rather than silently treating simulated, stale, malformed or missing data as a legitimate machine diagnosis. No feedback to L1 decisions or hidden L2 influence on the 104B protected core.

## 4. Components and responsibilities

### A. L2 Input Adapter and Quality Gate
- Accept only explicit versioned **synthetic** offline input in V0.1; no OS APIs in pure analyzer.
- Coarse event types proposed: `SESSION_BEGIN`, `SESSION_END`, `ACTIVITY_HINT` (IDLE/INTERACTIVE/BACKGROUND/UNKNOWN), `L1_CONDITION` (R2.1 state, pressure mask and source quality), `GAP`, `RESET`. All are simulated; **no real keyboard/mouse tracking**.
- Each row: monotonic-ms, source type, trust/provenance, sequence, quality, type, bounded value. No walls-clock, usernames, PIDs, process names/commands, window titles, file paths, document names, IPs, URLs or network payloads.
- Externally indicated L1 quality must be preserved, not represented as real timestamp confidence. Explicit invalid/unknown enum and out-of-range values => UNKNOWN; time/sequence regression => reset or abstain, not fabrication.

### B. L2 Context Engine (pure C11)
- Single deterministic state machine, no global mutable state, no kernel/service API or heap per event. Proposed states: `UNKNOWN`, `IDLE`, `INTERACTIVE`, `BACKGROUND_BUSY`, `RESOURCE_CONSTRAINED`, `MIXED`, `TRANSITIONING`.
- State is inferred only from sufficient, recent *explicit* simulated activity hints and validated L1 pressure descriptors. L1 memory pressure safety is not downgraded by L2 inference.
- Invalid events, missing context, long gaps, contradictory signals and resets cause UNKNOWN/TRANSITIONING and **no resource-saving claim**. Describe reason codes and evidence support; do not emit probabilistic confidence from arbitrary thresholds.

### C. Episode Ledger and Device-local Context Summary
- Store bounded episode counts/duration buckets, observed transitions, last known context and unknown/gap counts; **aggregate only**, not raw event contents. Reset/restart/generation semantics versioned and explicit.
- A V0.1 summary must be deterministic across identical histories and explainably different across materially different synthetic histories. That is **engineering behavior**, not yet proof of improved device individuality.
- No external memory service, Mnemos integration, semantic embedding, cloud requirement, automatic L3 memory import or cross-device sync in V0.0/V0.1.
- Suggested prospective limit: <=8 KiB L2 runtime model state, <=16 KiB serialized checkpoint **if a later version authorizes persistence**. V0.1 should have **no persistence by default**; exact structures/budgets are finalized before implementation.

### D. Explanation and Proposal Composer
- Separate `L2ContextSnapshot` from `L2Proposal`. A proposal has: candidate action kind, synthetic evidence references/reasons (not raw private rows), expected benefit *hypothesis* (not measured), risk band, conditions/expiry, missing evidence, guard reasons and human decision status.
- V0.1 proposal states `NONE`, `ASK_USER`, `BLOCKED`. Do not create `APPROVED` or `EXECUTED` from model output. Human-consent evidence cannot be fabricated by tests.
- Candidate **text-only** proposals for V0.1: “Consider deferring simulated noncritical maintenance until idle” and “Investigate sustained memory-pressure condition; no automatic change.” No executable command, shell snippet, service name, cgroup write or auto adaptation.
- Contradictory/invalid input or potential core-safety conflict => `BLOCKED`/abstain; never recommend violating protected L1 priority. Avoid false certainty and false performance-benefit assertions.

### E. Authority, Validation and Audit (future-proof design, no execution)
- Treat input and proposal requests as untrusted; strict schema, bounds, canonical encoding, reason identifiers and provenance.
- A *future* action-capable system would require a capability-scoped OS broker **separate from** the observer, a typed allowlist, explicit ephemeral human approval, per-action preconditions, dry-run, timeout, rollback, logging, replay resistance and automatic stop on unsafe context. It must never take untrusted natural-language shell commands.
- V0.0/V0.1 contains **no broker, privilege, action socket, daemon or runtime L1 policy writer**. Proposed future authority does not grant it.

## 5. Interfaces: contract proposal, not final ABI yet

V0.1 engineering contract should be frozen in a separate preregistration commit *before executable code*. Candidate struct concepts (field names/sizeof not yet approved):
- `L2EventV1`: schema version, monotonic time, sequence, quality/provenance, event kind and bounded enum-only payload.
- `L2ContextV1`: state, reason bitmask, evidence count/quality, last valid time/generation, bounded aggregate counts.
- `L2ProposalV1`: action kind **TEXT_ONLY**, reason code, risk, expiry and explicit `requires_user_approval=true`; no executable command path.
- `l2_init`, `l2_step_event`, `l2_snapshot`, `l2_compose_proposal`, each deterministic and pure except mutation of its own passed instance.

**Cross-layer contract:** L1 can supply a copy of R2.1 descriptive state/quality and optional R2.2 aggregate summary through a **read-only adapter**. In V0.1, fixtures simulate those values; do **not** import/call L1 live sensors or expand privileges. L2 does not call `l1_step_at`, modify `L1Core`, link to actuators or change L1 learner state. Version and reject unknown descriptors rather than silently casting unknown enum values.

## 6. State transitions: an illustrative synthetic trace

```text
SESSION_BEGIN
ACTIVITY_HINT=INTERACTIVE (valid)
L1_CONDITION=QUIET (valid)           -> INTERACTIVE (descriptive)
ACTIVITY_HINT=BACKGROUND (valid)
L1_CONDITION=IO_PRESSURE (valid)     -> BACKGROUND_BUSY or MIXED
GAP / missing source                -> UNKNOWN; suppress proposal
RESET                               -> UNKNOWN; clear volatile context
ACTIVITY_HINT=IDLE + valid inputs   -> IDLE (after a preregistered support gate)
```

Different histories can create different bounded context summaries but **identical safety advisories** when fed to existing L1 core. This does not prove L2 understands real user workflows.

**Truth separation:** runtime engine sees only events, **not** labels. Independent synthetic scenarios carry separately frozen truth about coarse OS context and appropriate *proposal states*. No "we generated it, therefore we proved intelligence" conclusions. In particular, PSI alone cannot distinguish web browsing, compiling software, creating art or a user's intent; those require future explicit, permissioned additional context.

## 7. Phases, freeze/acceptance points and versioning

| Stage | Build | Acceptance gate |
|---|---|---|
| **L2 V0.0** (this PR) | Architecture, threat model, data/authority boundaries, evaluation plan, Codex handoff | Documentation/design reviewed; no running code |
| **L2 V0.1** (future separately authorized) | Offline, deterministic synthetic event parser + pure C11 context state machine + context report, no persistence/action | Independent fixtures; no invalid-to-confident transition; byte-equivalent legacy L1; bounded CPU/RSS |
| **L2 V0.2** | Bounded episode context and drift/recovery on synthetic histories; explicit unknown support | Better context reliability versus competitive fixed finite-state baseline; independent heldout under fresh frozen study |
| **L2 V0.3** | Local text-only, risk-filtered, explainable proposal output | No false executable authority; user preference/consent simulation not falsely treated as approval |
| **L2 V0.4** | Optional finite, explicit opt-in **guest-only** observation feasibility | Requires new privacy/security/recording approval, time bounds, no automatic service, no OS writes |
| **L2 V0.5+** | Evaluate capability-broker architecture and rollback **on simulated fake resources first** | Separate user approval, safe/unsafe negative tests, actual resource benefit proof before any live guest actuation |

No L3 data source or action coupling ships until an entirely separate decision. A synthetic milestone may still legitimately return scientific NO_GO.

## 8. Proposed resource & dependency budget (prospective, not qualified)

Aim for **single-threaded C11**, pure core, fixed arrays, stdlib-only build tooling and streaming offline parser. No Python interpreter or large ML framework in the deployed core. Python may generate offline synthetic data/CI fixtures, not become a runtime dependency.

Before V0.1 coding, formally freeze: state bytes <=8KiB, whole analyzer process RSS <=8MiB on Debian QEMU, constant bounded per-event work, 100,000-row finite replay (or a stricter justified exact bound), no per-event heap and no hidden daemon. Median CPU <=50 microseconds/event, measured individual p95 <=250 microseconds/event as **initial design targets subject to preregistration review**. These are overhead limits, **not** proven system resource improvements. Report timer overhead, valid quantiles, NDEBUG/ASan differences, VM noise and old R2.3b p95 margin lessons.

## 9. Mandatory safety decisions and scientific honesty

- Keep all protected L1 original artifacts and numeric meanings intact: 104B core, 208B shadow, 72B old state, R2.1 classifier, R2.2 112B memory/80B checkpoint, optional read-only R2.3c harness and historical source-hash evidence.
- L1 R2.3/R2.3b invalid results and R2.3c PASS are independent facts. L2's initial experiments do not retroactively change any.
- `ADAPTATION: NO_GO`, `ACTION_COUPLING: NO_GO`, `REAL_EVIDENCE: INSUFFICIENT`, `FORECAST_TRANSFER: UNDETERMINED`, `R2_UTILITY: UNDETERMINED`, `R2_INDIVIDUALITY: UNDETERMINED`, `PRODUCTION_AUTHORIZATION: BLOCKED`, `V1_2_BENEFIT_EXPERIMENT: BLOCKED` remain binding.
- No passive surveillance, keystrokes, window titles, app commands, URL histories, credentials, user identities, network/packet capture, guest OS actuation or Windows host modifications. The host and guest's ordinary OS integrity rules always prevail.
- No *actual* L2 workflow-awareness or individuality is established by this document. Engineering future APIs do not grant execution authority.
