## Why V0.1 is different from L1 research and first L2 draft

The demonstration is not another PSI heuristic or coarse classifier. It is an initial **fixed-memory experience structure**: associations between **synthetic functional roles and workspace handles**, plus repeated ordered routines, with conservative textual suggestions. Fast context may change in a minute; repeated session-level associations create slower identity and can co-exist across work modes.

V0.1 does **not** infer someone's occupation or actual actions, label a profession, read private folders, create templates, launch apps, change performance controls or learn real preferences. We evaluate **engineering representation** only, not useful AI individuality.

## Codex deliverables, ordered commits

### Phase 1 — Schema/fixtures and independent preflight (first *implementation* commit; BEFORE model C code)
- Read both merged V0.0 plans, this handoff and the frozen V0.1 contract completely.
- Use stdlib-only Python to generate tiny, exact known-answer CSVs A, B, MIXED, COLD, RESET_LATE, GAPPED, INVALID, PRESSURE_BLOCK and capacity/saturation fixtures. No full V3 scientific corpus or actual OS observations.
- Implement a separate data verifier: canonical schema, sequence/timestamps, allowed enum placement, zero personal strings, actual eligible completed sessions, discarded interrupted sessions, expected transitions/triples and reset-aware support.
- Negative cases must demonstrate rejection of wrong nominal sessions, duplicated/ambiguous row identity, late reset with insufficient *post-reset* history, invalid row admitted to routine, wrong enum/source, stale context and fabricated support. Canned simulator expectations may be used for fixture verification; state machine code remains separate.
- Commit generator, independent verifier, tiny fixtures and SHA-256 manifest **before implementing** `src/level2` analyzer. If unable to create a valid, support-complete fixture, mark engineering blocked and stop instead of changing the frozen protocol retroactively.
- Keep fixture sizes modest and avoid spilling unnecessary raw rows into reports.

### Phase 2 — Pure deterministic C11 core
- Implement `src/level2/l2_state.h` and `src/level2/l2_state.c` with caller-owned fixed `L2State`, bounded session-role buffer, context and workspace graph/routine slot arrays; no heap, network, clock, filesystem or OS API inside the core.
- Provide a separately tested strict offline input parser, e.g. `l2_fixture_cli.c` reading an explicitly supplied synthetic file only. No live capture or auto-start.
- Suggested pure APIs: `l2_init`, `l2_step`, `l2_snapshot`, `l2_query_workspace`. Exact ABI must reflect the frozen wire contract and be documented; deny unknown versions/enum values.
- Match frozen per-session commit semantics (only valid `SESSION_END` of >=3 roles credits a session); deterministic counts, table exhaustion/eviction, aging every 16 sessions, cold start, reset and context freshness; candidate role-triple selection and query nonmutation.
- Implement a bounded report with enumerated role codes, reason codes and actual supporting session/edge/triple counts. No arbitrary command strings or raw input identity dumps.
- Tests: `sizeof(L2State)<=8192`, fixed upper bounds on nodes (16), edges (32), routines (16), pending roles (8), no silent truncation/overwrite, deterministic bytes when inputs equal; changed histories create explainably different *in-memory* associations.
- A's highest supported 3-role candidate must be `CODE_EDIT|BUILD_TEST|DOC_VIEW`; B's `REFERENCES|CANVAS|ASSET_GROUP`; the MIXED fixture supports both workspace modes; COLD/LATE_RESET abstain; identical invalid/pressure cases make both abstain; no literal profession labels in code.

### Phase 3 — Fault injection and measurement
- Normal and NDEBUG strict C11; ASan/UBSan/leak, invalid tokens/overflows/negative/zero/duplicate/regressed sequence, timestamp reset/unknown inputs, partial session abort, stale descriptor, unsupported model query, ambiguous multi-mode, full graphs and saturated/aged counts.
- Replay >=100,000 **synthetic** events with bounded output/memory; run optimized median CPU <=50us/event and **individual-call p95 <=250us/event**, including parser costs if reporting aggregate CLI timing; model <=8KiB and entire analyzer <=8MiB guest RSS. Report timing source/overhead and failures honestly.
- Baseline frozen source audit: protected L1 104B core actions/state, 208B shadow, legacy policy/persistence, R2.1 descriptor, R2.2 operational memory, R2.3c preflight and historical verdicts exactly unchanged. Normal `make rc0-ci`, `make rc0-qualification` inside isolated Debian QEMU must pass.
- New L2 test target may be separate from legacy level1 CI if integration only *adds* checks; do not weaken or replace previous tests.

### Phase 4 — Publish without merge
- Write `docs/L2-v0.1-validation.md` with commit sequence, fixture/regenerator IDs, test matrix, memory sizes, graph/routine counts for A/B/mixed, refusal reasons, CI/debian status and scientific limits.
- Report `L2_V0_1_ENGINEERING: GO|NO_GO` separately from `L2_EXPERIENCE_STRUCTURE: DIVERGENT|NOT_DIVERGENT`. Real-world appropriateness/utility remain `UNDETERMINED`.
- Push to existing **draft PR**; leave unmerged pending independent review and explicit merge permission. If data, tests, or benchmark gates fail, publish a clean negative result rather than moving post-hoc thresholds.

## No action/monitoring authority

Never implement a production observer, guest PSI reader, process/folder/window scanner, keyboard monitor, system service, cron task, telemetry recorder, file mover, cgroup scheduler writer, Windows registry/host modification, L1 policy updater, L3 agent, automatic approval or online model download in this milestone.

The only allowed runnable program is an **explicitly invoked finite offline fixture analyzer**, running inside the isolated Debian QEMU guest against synthetic files.

A virtual workspace candidate is an **enum-only description** of a possible arrangement, not an action that has been performed. Future real OS observations and real user outcomes need separate opt-in and research approvals.

## Freeze / version discipline

Any substantive adjustment to event grammar, capacities, support thresholds, failure precedence, candidate selection, resource limits or known-answer hypotheses after fixture freeze is **a new versioned experiment**; preserve original frozen records and don't re-label failures as PASS by editing data. Implementation bug fixes within contract are allowed with transparent tests and review, but no heldout utility dataset is used in V0.1.

**Current task after this docs-only setup:** Codex can use this plan to implement the authorized synthetic-only V0.1 prototype, with corpus-first discipline and independent CI review. No background work is happening until execution is actually invoked.
