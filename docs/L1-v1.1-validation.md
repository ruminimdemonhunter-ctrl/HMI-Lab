# HMI Level 1 V1.1 proposal-boundary validation

## Scope and conclusions

V1.1 implements a bounded offline behavior-memory proposal validator. It does
not authorize or apply proposals to a live L1 process.

    PROPOSAL_VALIDATION: GO
    PRODUCTION_AUTHORIZATION: BLOCKED
    L2_DEPLOYMENT: NOT_AUTHORIZED
    ADAPTATION: NO_GO
    ACTION_COUPLING: NO_GO
    FORECAST_TRANSFER: UNDETERMINED
    REAL_RESOURCE_BENEFIT: NOT_ESTABLISHED

Protocol: `bcdf008b1ba3bbccfb3041d52d5154c16a047f33`. Base:
`599c08c2203af72806a1594b5750a37f6bf49a66`. Specification: Issue #17.

No production L2/L3 component, network service, key, cryptographic primitive,
resource actuator, scheduler/cgroup interface, PSI trigger, Windows host
change, or long PSI capture was introduced.

## Boundary design

`l1_proposal_parse()` accepts only the frozen nine-line, LF-terminated,
ASCII canonical envelope in exact field order. Input is capped at 4,096 bytes
and ten lines. Empty decimals, signs, leading zeros, overflow, whitespace,
control characters, CRLF, NUL, missing/duplicate/reordered/unknown fields,
trailing bytes, unsupported schema and behavior values outside the existing
compiled policy limits are rejected.

`l1_proposal_check()` requires the envelope's base generation to equal the
test-supplied current core generation and the proposed generation to be
strictly greater. It calls the unchanged `l1_policy_valid()`.

`l1_proposal_read_file()` requires an explicit bounded absolute Debian path
without `.` or `..` components. It opens `/` and resolves every directory and
the final file component with bounded `openat()` calls and `O_NOFOLLOW`, so a
symlink at any position is rejected. It accepts only a same-UID regular file
without group/other write permission, rejects files outside 1..4,096 bytes,
reads exactly the declared size, and reopens the component chain to check
descriptor/path identity plus size/mtime/ctime after reading. These are local
race-reduction measures, not authentication against a malicious same-UID
writer, privileged process or hostile storage.

The production `l1_proposal_check` executable validates only offline
structure, safety and generation. Its output always includes:

    authority=none production_apply=blocked
    PRODUCTION_AUTHORIZATION:BLOCKED
    L2_DEPLOYMENT:NOT_AUTHORIZED

There is no `--authorize` option, environment authorization, source trust
label, sidecar verdict, persistence write or live-core application.

## Test-only authorization seam and isolation

Only builds compiled with `L1_TESTING` expose
`l1_proposal_test_apply_clone()`. It:

1. copies at most 4,096 exact proposal bytes into bounded local storage;
2. parses and checks those bytes;
3. requires an injected mock verifier to approve those exact bytes;
4. copies the supplied `L1Core`; and
5. calls the existing `l1_apply_policy()` only on that disposable copy.

An absent or negative verifier denies. Mutation relative to the verifier's
expected bytes denies. A self-declared authorization field is malformed.
Every rejection leaves both the current core and result sentinel byte-for-byte
unchanged. Acceptance resets the clone to HOLD with fresh confirmation,
retains the existing memory-over-I/O-over-CPU priority, and exercises
monotonic rollback with the unchanged core implementation.

The mock proves API sequencing and exact-byte binding only. It contains no
secret, protected identity, key lifecycle, established authentication
provider, durable replay store or privilege separation and cannot be reused as
a production trust anchor.

## Adversarial and compatibility coverage

The deterministic corpus covers:

- canonical generation 1, distinct future generations, UINT32 maximum
  generation and every compiled threshold/confirmation boundary;
- duplicate, unknown, reordered and missing keys; wrong magic/schema; blank,
  truncated and trailing content; CRLF, NUL, spaces and controls;
- negative, signed, leading-zero, overflow and zero/stale generations;
- replay/base mismatch, verifier absence/rejection and exact-byte tampering;
- relative/parent/oversized paths, symlink, directory, device, unsafe mode,
  oversized file and deterministic replacement after read;
- active-action clone acceptance, HOLD reset, fresh confirmation, priority,
  rollback and byte-for-byte rejection isolation; and
- existing CRC corruption recovery, V1 migration, 72-byte V2 persistence,
  parser, replay, shadow separation and historical evaluation tests.

## Why production authorization remains blocked

The legacy `l1_monitor --policy` interface accepts an unauthenticated
development text file. It validates shape and safety bounds but not author or
authority, so it would bypass any claim that this new offline tool protects a
live process.

The 72-byte V2 state has CRC32 for accidental corruption. CRC32 is not a MAC
or signature, the format contains no authentication key, and filesystem
replacement can replay an older valid state. Process-local generation checks
therefore do not provide reboot-persistent anti-rollback against hostile
storage.

A future production proposal path requires separate architecture and review:

1. an approved established authentication/authorization provider;
2. a protected trust anchor and key provisioning, rotation, revocation and
   recovery lifecycle;
3. independent protected monotonic generation/replay storage across reboot;
4. a single audited apply path that removes or securely blocks the legacy
   `--policy` bypass;
5. atomic verified-byte handoff into the applying process with failure audit;
6. least-privilege ownership and update policy for proposal/state storage; and
7. rollback, disaster recovery and compromise-response procedures.

No later milestone may infer authorization from this test-only GO.

## Reproduction and measured results

Validation ran sequentially in the existing unprivileged Debian QEMU guest
with Linux `6.12.113+deb13-amd64` and GCC `14.2.0`. Source was transferred
with the repository's bounded `scripts/sync-source.ps1`; no real PSI capture,
workload generation, privileged operation or resource-control write ran.

The canonical example SHA-256 is
`fc689e52133e74c68419941351aeb58f74ab8e8dd7d64526a224fc33e1ff7f04`.
This digest is a reproducibility identity only, not proposal authentication.

The following commands passed:

```sh

make test-ndebug
make sanitize
make proposal-ci proposal-bench-sanitize-ci
make clean all replay evaluation-ci evaluation-v05-ci evaluation-v06-ci \
  evaluation-v07-ci recorder-bench-ci inspect-ci evidence-ci proposal-ci
```

generation, authorization-denial, clone-isolation, rollback and filesystem

## Limitations and discrepancies

- File identity and permission checks reduce ordinary local races but cannot
  authenticate a same-UID writer, privileged actor or hostile filesystem.
- The mock verifier establishes control-flow and exact-byte binding in tests;
  it provides no real identity, cryptographic authenticity or protected
  replay state.
- The benchmark includes process startup, file validation and parsing for two
  child executions. It is not decision-core latency and the five repetitions
  are too few for distributional performance claims.
- No production authorization path or real L2 integration was exercised, and
  no resource or real-world benefit is inferred from these tests.
- No deviations from the frozen V1.1 protocol or unresolved validation errors
  were observed.

## Post-review hardening and rerun

Independent review of commit `80e60e0d634451665bc45a9df54acd8777d1d99e`
identified two narrow correctness gaps after the original measurements above.
This section appends the corrections and rerun; it does not replace the frozen
protocol or silently rewrite the original evidence.

First, `l1_proposal_test_apply_clone()` now rejects an exact alias between its
`current` and `result` `L1Core` objects before parsing, verifier invocation or
any write. A deterministic regression supplies canonical bytes and a positive
exact-byte verifier with both pointers aliased, then verifies an
`invalid-argument` rejection and byte-for-byte preservation of the core.

Second, the proposal loader now walks each component from `/` using
`openat()` with `O_NOFOLLOW`; parent components additionally require
`O_DIRECTORY`. It no longer relies on final-component-only `open()` and
`lstat()`. The opened descriptor is checked before and after reading, and the
same component chain is reopened after the test race hook to confirm the
named file's device, inode, size, mtime and ctime. A valid nested-directory
fixture succeeds, while the same file addressed through a symlinked parent is
rejected as an unsupported file type. Final symlinks, concurrent replacement,
ownership, mode, type and size regressions remain covered.

The complete Debian QEMU sequence passed again:

```sh
make clean all test
make test-ndebug
make sanitize
make proposal-ci proposal-bench-sanitize-ci
make clean all replay evaluation-ci evaluation-v05-ci evaluation-v06-ci \
  evaluation-v07-ci recorder-bench-ci inspect-ci evidence-ci proposal-ci
make proposal-bench
```

Normal, `NDEBUG`, ASan, UBSan and leak tests passed. Persistence corruption,
V1 migration, exact 72-byte V2 state, replay, V0.4-V1.0 historical
evaluations, recorder, inspector and evidence tests also passed. The V0.4,
V0.5 and V0.6 development/training/held-out identities listed above, V0.7
identity checks, and V1.0 `f2aca8af7c6ddd3c`/`0bbd76851e142c45` fixtures did
not change. `L1Core` and `L1Shadow` remained 104 and 208 bytes. No core,
policy, state, learner, generator or frozen experimental input changed.

Five new optimized repetitions, with the same canonical-valid plus 4,096-byte
negative pair, measured:

| Metric | Median | Min | Max |
|---|---:|---:|---:|
| combined process CPU | 5,451,000 ns | 4,334,000 ns | 11,625,000 ns |
| wall time | 6,178,000 ns | 5,151,600 ns | 12,821,100 ns |
| peak RSS | 1,424 KiB | 1,392 KiB | 1,500 KiB |

The optimized RSS result again passes the frozen 8,192 KiB budget. The new

The corrections close the reviewed isolation and path-traversal gaps without

historical scientific NO-GO conclusions remain in force.
