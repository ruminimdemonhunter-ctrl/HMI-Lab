# HMI L1 V0.9 — frozen transparent-replay and acceptance protocol

**Status:** preregistered initial branch commit; freeze before implementation and before any V0.9 held-out scoring.

**Base:** merged V0.8 at `1cff0d2e0d39c4aee1a8098665f0a82177b76f5f`. **Program:** [issue #13](https://github.com/ruminimdemonhunter-ctrl/HMI-Lab/issues/13).

## Purpose and scientific scope

Build a human-inspectable, deterministic, *read-only* replay demonstration from the **actual compiled L1 core and shadow learner**, not a simulated replacement algorithm. The owner will personally assess usefulness after engineering stabilization, not after each experiment. Passing V0.9 means `REPLAY_READY`, **not** `ADAPTATION_GO`, `REAL_BENEFIT_GO`, or hardware control.

The original HMI direction is tiny C11 hardware-near L1, immutable safety, compact versioned behavior memory, extremely bounded slow self-adaptation, a future validated L2-only behavior-memory proposal path, and no L3->L1 writes. The actual state of V0.8 is a 104-byte advisory decision core, 208-byte shadow, 72-byte V2 memory format, synthetic evaluation and read-only PSI recorder. No demonstrated OS/hardware savings. Preserve all prior verdicts:
- V0.8 `RECORDER_EFFICIENCY: GO`; `REAL_EVIDENCE: INSUFFICIENT`
- V0.7 `DIAGNOSTICS: NO_GO`
- V0.6 `SHADOW_PREDICTION: NO_GO`; `ACTION_COUPLING: NO_GO`.

## Freeze boundaries

1. **No changes** to `l1_core.c`, `l1_shadow.c`, `l1_policy.c`, `l1_state.c`, their public semantics or compiled safety priorities; no changes to historical evaluators, manifests, seeds or results. Existing action/priority order memory > I/O > CPU > HOLD stays immutable. Parser/adapter correctness fixes must be independently identified, separately tested and reported; no silent scope extension.
2. No unprivileged/privileged OS actuation, PSI trigger writes, cgroup or scheduler writes, firmware/hardware control, networking/upload, remote commands, L2/L3 functionality, or host Windows modification.
3. No automatically generated resource pressure. Only finite, opt-in CLI invocation inside the Debian QEMU guest. No research-length PSI capture in this milestone without a separate explicit, finite user authorization specifying guest-local output.
4. No dynamic allocation in L1 core or shadow hot path. Viewer may use bounded stack or static storage. All inputs bounded to frozen V1 limits (16,777,216 bytes/file; <=86,400 rows; <=512 bytes/line) and output caps. No raw real trace commit/upload. Respect mode-0600 guest trace privacy.

## Frozen inputs

Three disjoint input types, never conflated:

- **Synthetic fixture stream:** a small new deterministic offline `demo` suite (not a stochastic held-out experiment) whose labeled, inspectable event sequence is committed alongside tests. Named cases: idle/noise, rising CPU, urgent memory, sustained I/O, simultaneous pressure/priority, invalid telemetry, monotonic regression, reset/recovery, memory-policy invalid/replay/rollback. Provide exact expected action sequence and checksum with `l1_step_at()` as the source of truth; references should be committed *prior* to any final evaluation run. No tuning.
- **Existing frozen synthetic evaluation:** existing v0.4–v0.7 tests with their checksum/manifest gates, invoked unchanged for regression. V0.9 must not claim a new forecasting efficacy trial from these cases.
- **Already-recorded guest-local V1 trace:** optional explicit file from the guest, parsed strictly using `l1_trace_read()`. No latent oracle labels, no causal savings claims; explain published decisions vs shadow forecasts observationally. A too-short trace is a valid parser demo but is NOT a scored real forecast study.

The viewer shall not infer 'future observed outcome' before the specified future interval. If it displays predictor feedback, label pending/unavailable/evaluated and missing reason. Never attribute off-line ground-truth values to live telemetry or claim real effect from hypothetical actions.

## CLI design contract

Implement `l1_inspect` in `src/level1/` using existing modules, strict C11 and minimal dependencies, with the following bounded operations:

```
./l1_inspect demo [CASE_NAME] [--details MAX_ROWS]
./l1_inspect trace ABSOLUTE_GUEST_PATH [--forecast-config live-default|v06-trained] [--details MAX_ROWS]
./l1_inspect help
```

- `demo` defaults to a small documented finite fixture catalog; `--details` is capped to <=2,000 rows; default summary or <=60 detail rows. Reject unknown options, unsupported trace schema and unsafe paths; never create/modify inputs or write a policy/state file.
- Deterministic output schema and versioned header with source type, policy generation and thresholds, row counts, forecast class, action name, fallback state, and separate shadow status. Use actual `l1_action_name`; comparisons must run genuine `l1_step_at` and `l1_shadow_step_at`, not a rewritten rules engine.
- Explanations: show **observable and compiled** reasons (e.g. input valid, measured pressure, active priority, current confirmation/candidate state, eligibility, policy thresholds) without falsely asserting causal reasons that core does not expose. If the chosen action depends on hidden history, label the explanation as a bounded diagnostic summary rather than fabricated rule proof.
- Compare only explicitly configured modes: policy-fixed and v0.5 risk-aware action recommendation, and shadow predictor with either `800/40/150` live default or `2000/75/600` v0.6 trained thresholds. Never conflate model's forecast with the published action. Keep independent core instances per comparator with identical samples/timestamps.
- Test a paired observer-off reference runner with identical serialized `L1Core` bytes and `L1Action` on every sample; output must not influence core behavior. It is permitted that core transitions advance naturally during replay, but **not** that logging feeds back into decision logic.
- For trace parsing, validate the complete file and footer checksum before announcing it `verified`; if streaming text before EOF, mark unverified until final checksum succeeds, or use safe two-pass validation with TOCTOU/atomicity caution. Do not mislabel corrupted input as valid.

## Acceptance and performance

- Exact reproducible output for bundled demos (checksums, priorities, invalid cases, fallback, policy generation/rollback); strict golden tests stable across repeated invocation.
- Zero core/action mismatches between accompanied and unaccompanied shadow/viewer runs. Exact unchanged V1->V2 state migration behavior and 72-byte V2 encoding.
- Proven bounded file, row, argument and output sizes, no FD leaks, no raw user-specific data committed, no false positive `validated` marker.
- On Debian QEMU, optimized CLI replay peak RSS <=8,192 KiB on full max-size bounded fixture. Measure CPU separately for core+shadow, parser and formatted output; do not use stdout terminal throughput as an alleged intelligence speed metric. Report median, range, compiler and guest details; no adaptive algorithm or policy tuning.
- Build/test/ NDEBUG / ASan / UBSan / leak / parser-negative-corpus / persisted-state / replay / V0.4–V0.8 exact historical identities remain passing. Integrate bounded CI and sanitizer smoke.
- Research decision:
  `REPLAY_READY: GO` if all of the above tests, safety invariants, demo semantics, and limits pass; otherwise `REPLAY_READY: NO_GO`.
  `ADAPTATION: NO_GO`, `ACTION_COUPLING: NO_GO`, `REAL_RESOURCE_BENEFIT: NOT_ESTABLISHED` remain explicit regardless of replay quality.
