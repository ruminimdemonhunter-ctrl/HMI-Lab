# HMI L2 V0.0 — Architecture acceptance and prospective OS-context research protocol

**DESIGN-STAGE PROTOCOL ONLY. NOTHING IN THIS DOCUMENT IS A VERIFIED L2 RESULT.**

- Accepted baseline: L1 R2.3c merged `main` SHA `74e2bd3d05cebc941742c5a67c545172a5b6b5c3`.
- L2 architecture: `docs/L2-v0.0-architecture.md`. Tracking issue [#33](https://github.com/ruminimdemonhunter-ctrl/HMI-Lab/issues/33).
- Current permitted scope: docs-only L2 V0.0. **No L2 executable, synthetic corpus generation, real guest sensors, persistent profiling or OS execution**.
- Historic experimental PR #28 and #30 remain unmerged/INVALID; L1 action-coupling NO_GO, production authorization BLOCKED.

## 1. Separate levels of evidence

Keep distinct verdicts for:
1. **Documentation soundness:** clear interfaces, actors, budget, privacy, failure cases and reviewable test plan.
2. **Engineering integrity (future V0.1):** deterministic strict parser, immutable safety core, strong UNKNOWN/fail-closed and bounded overhead on generated OS-context events.
3. **Synthetic contextual recognition (future V0.2):** independently labeled coarse situation/episode classifications distinguish a specific context from a fair fixed finite-state baseline.
4. **Contextual proposal usefulness (future V0.3):** risk-filtered, correct explanation, demonstrably fewer false/intrusive suggestions versus simple always-NONE / fixed baselines on independent heldout.
5. **Real device benefit or individuality (separate later study):** independent, opt-in real data and user outcomes with ethics/privacy and different device histories. Not established by synthetic GO.
6. **Resource action authority:** a separate security/deployment authorization, NEVER implied by any of 1–5.

An L2 program may have contextual categories without correctly identifying a user's current task. If evidence does not support a category, label it UNKNOWN. Distinguish synthetic source truth from real-world truth and avoid "understanding" as an unqualified empirical claim.

## 2. V0.0 design review acceptance

The documentation stage is reviewable when all are explicit:
- Named responsibilities, interactions and prohibitions of L1/L2/L3; conventional OS and L1 compiled safety remain authoritative.
- Read-only L1 descriptive inputs, independent OS synthetic activity hints, monotonic freshness/provenance/quality and fail-closed gaps/resets.
- Pure deterministic L2 core, bounded episode memory, non-sensitive counters and debuggable reasons (never unexplained confidence).
- Clear proposal vs actual execution separation; no privileged paths or automatic action loops.
- Explicit data-minimization policy; **no real personal context collection by default**, no ephemeral/snapshot export of names, command lines, titles or network content.
- Test-first V0.1 phases and synthetic corpus freeze requirements, baseline fairness, finite resource budgets and stop conditions.
- Exact restriction: **V0.0 has no C11 implementation, no CI outcome, no real-world evidence and no actuation.**

A doc review may return `NEEDS_REVISION` without affecting accepted L1 work.

## 3. V0.1 — future safe implementation prerequisites

**Before a single line of V0.1 executable code** open a new issue and branch from latest accepted main, and commit:
- **V0.1 frozen external event v1 schema:** fixed endianness/text grammar, headers, numeric ranges, monotonic/sequence rules, explicit source/provenance, quality, activity hint and simulated R2.1 condition enum; bound unknown enums; strict finite max input size.
- **V0.1 frozen state-machine transitions:** exact support thresholds, contradictory-hint precedence, liveness gap limits, unknown/reset/restore semantics, episode boundaries, bounded counters and overflow behavior. No learning implied.
- **V0.1 frozen API:** immutable input, state-mutating only a caller-owned L2 context instance, read-only explanation, deterministic output; no L1 pointer or OS write interface.
- **V0.1 frozen resource limits:** candidate <=8KiB L2 state, <=8MiB process RSS, finite replay >=100,000 events; prospective median <=50us/event and individually clocked p95 <=250us/event on isolated Debian QEMU; adjust any target only *before* measurement with explicit scientific rationale.
- **V0.1 frozen negative tests:** malformed schemas, invalid ranges, negative timestamps/sequence regression, gap, missing L1, stale L1, contradictory activity vs pressure, cache/reset, invalid quality, corrupt snapshot, resource exhaustion, prompt-injection-looking text, unknown source, event flood and deduplicated repeat.
- **V0.1 frozen data limits:** no host traces, no live PSI or process monitoring; strictly generated labeled fixtures; generator + independent manifest verifier committed *before* context algorithm code (avoid the R2.3/R2.3b failure pattern). Before freezing fixture hashes, run the proposed **exact state machine** against the simulated streams to prove required support states and that test episodes are eligible. Commit that preflight evidence and include a failing injected negative fixture.
- **V0.1 no privileged or unprivileged actuation**, no actual user consent, no L1 policy writing.

The exact V0.1 support sample numbers and thresholds are *not set by V0.0*; do not infer them from L1's 256/4 rule, which belongs to the different R2.2 operational-memory contract. Freeze them in V0.1 after architecture review.

## 4. Reproducible corpus / calibration and held-out sequencing for V0.2+

Avoid another invalid R2.3 type result:
1. Protocol and expected support/eligibility rules FIRST.
2. Deterministic, independent **two synthetic device contexts** generator and post-exclusion/schema verifier next. Independently derive labels from a predeclared simulation truth rather than from predictor output.
3. Include IDLE, INTERACTIVE, BACKGROUND_BUSY, RESOURCE_CONSTRAINED, MIXED, UNKNOWN, gaps, contradictory signals, recovery, planned maintenance proposals; be cautious that interaction labels themselves can trivially reveal the answer. Include indistinguishable-signal negative controls and avoid claiming impossible inference.
4. Each device: disjoint training (if any), calibration and **untouched heldout**, independent episode IDs; no duplicate event windows presented as independent incidents. All data identities SHA-256 locked before model implementation.
5. Fair baseline: capable deterministic fixed rule or finite-state comparator using the *same allowed inputs and same latency/quality constraints*, calibrated only on calibration fixtures. Include always UNKNOWN, always NONE (proposal) controls with coverage.
6. A fresh calibration lock must bind actual source/config, generated corpus IDs, all selected parameters, baseline selection outputs and independently recomputed split checksums; assert no heldout open on invalid lock.
7. Only after a separate committed lock may a future user-authorized heldout run occur. Enumerate correct/incorrect context categories, unknown coverage, false reassurance and harmful proposals *per episode*, not just an overall percentage. No success by hiding failures in UNKNOWN.
8. Two different state histories may create different summaries; to claim appropriate individuality require *independent context-conditioned true labels*, two justified different decisions on identical probes, identical safety outcomes, and utility improvement against a competitive fixed baseline.

**V0.0 does not authorize any of these future study executions.**

## 6. Security adversaries and untrusted-source tests

Threats to predeclare:
- Malformed or attacker-controlled event fields, source confusion or adversarial sequence/timestamp ordering.
- Forged `quality=OK`, fabricated interaction event, or mislabeled machine profile.
- Filesystem path traversal/oversized input in offline CLI, output injection, leaking raw strings to logs.
- Replayed/tampered experimental checkpoint used as production authorization. CRC/SHA are **not** authentication.
- A proposal accidentally interpreted as a shell command, uncontrolled action dispatch or recursive L2->L1 policy updates.
- L3/cloud suggestion maliciously requesting privileged OS changes, protected policy bypass or surveillance (future; no L3 now).
- Workload regimes not represented in synthetic data, false confidence and cross-guest/host privilege confusion.

**Failure posture:** invalid input => abstain and give reason; protected L1 continues independently; no OS change. Report errors without including sensitive input. An offline test harness must prove it can't inadvertently create or execute an action by merely emitting a proposal.

## 7. Formal nonregression and review boundary

Immutable L1 protected code, 104B L1Core, 208B L1Shadow, 72B V2 persisted policy/state, R2.1 descriptor classifier, R2.2 112B operational memory/80B checkpoint, historical offline fixtures and scientific results. No L2 L1-policy-modifying interface in early phases.

Before declaring V0.1 engineering GO, run strict C11 with assertions and NDEBUG, ASan/UBSan/leaks, existing `make rc0-ci`, `make rc0-qualification` and protected source hash audit, Debian QEMU guest finite synthetic fixtures and individual-clocked performance measurements. Exact future CI additions cannot weaken historical tests; independent review before merge.

V0.0 remains **docs only**. It does not alter user settings, Windows host, Debian guest programs, real telemetry or production security settings.
