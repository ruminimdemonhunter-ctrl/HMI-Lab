# HMI L2 V0.0 — Adaptive Environment Engine: prospective evaluation strategy (revision B)

**DESIGN-ONLY. REPLACES CONTEXT-CLASSIFIER-ONLY EVALUATION FRAMING. NO L2 ALGORITHM OR EXPERIMENT HAS RUN.**

Based on `docs/L2-v0.0-architecture.md` revision B in [draft PR #34](https://github.com/ruminimdemonhunter-ctrl/HMI-Lab/pull/34), issue #33. This plan intentionally preserves accepted L1 R2.3c, invalid R2.3/R2.3b experiments and all L1 action/production NO_GO boundaries.

## 1. What to measure (do not substitute one outcome for another)

| Evidence level | Question | What counts | What does NOT count |
|---|---|---|---|
| A. Engineering | Does bounded L2 state safely process synthetic context and workspace sequences? | Validated schema, deterministic state, small memory, no OS actions, negative-case tests | Device personalization |
| B. Experience representation | Can two byte-identical instances retain demonstrably different **relations/routines** after different histories? | Explainable bounded graph/counter differences after staged simulated sessions | Correctness of suggestions |
| C. Context / proposal utility | Do memory-dependent recommendations match **independently declared** use situations better than competitive static/recent-history references? | Predeclared held-out per-session gains and safe false-suggestion rates for both devices | Synthetic labels as real user acceptance |
| D. Adaptation | Does acceptance/rejection/undo feedback improve future ranking under a change of habits without destabilization? | Independently judged outcomes, explicit undo, bounded hysteresis, regression tests | Unobserved implicit approval |
| E. Real-world transfer | Do voluntary users actually spend less effort with no harmful interruption or privacy breach? | Separate opt-in, scoped guest study with human feedback and reproducible metrics | Simulated traces |
| F. Permission to change OS | Is a reversible, capability-scoped action explicitly approved? | Separate broker security qualification AND explicit user authorization | Any of A–E by itself |

**No single synthetic test can establish real personalized OS intelligence.** Model explanations must be descriptive evidence, not probabilities or a claim of reading intent.

## 2. V0.0 document acceptance criteria

Before merging architectural docs, an independent review must confirm:
- L2 evolves a bounded *environment model*, not merely a fixed IDLE/BUSY classifier or occupational profile.
- Clear six-component architecture: input gate, fast context, workspace relations, routine history, proposal planner, outcome/reversal feedback.
- Two-speed adaptation, multiple concurrent work modes, expiration/negative feedback and cold-start abstention.
- Explicit privacy boundary: V0.1 inputs synthetic, opt-in only for future real machine/workspace signals; no actual file/path/content or Windows access.
- File organization strategy: **virtual views/templates and preview first**, physical file operations much later with separately authorized backup/rollback.
- No L1 writes, no runtime command executor, no background listener, no OS policy elevation.
- Prospective engineering/utility benchmarks, data freeze ordering, baseline fairness, separate approval for every future layer.
- An initial **evolving workspace memory in V0.1**, not just context classification.

V0.0 result vocabulary: `L2_V0_0_ARCHITECTURE: REVISED_PROPOSAL`, review `APPROVED|NEEDS_REVISION`. No L2 engineering pass can be claimed from a successful document commit.

## 3. V0.1 engineering contract — **freeze before implementation**

Create a new issue, branch and first protocol commit after architectural approval. No executable L2 code before it. Freeze exact:
- Strict event format (`L2EventV1`) with monotonically increasing uint64 timestamps/sequence, synthetic provenance, quality, workspace opaque ID, category/role enums and optional explicit simulated outcome.
- Events (proposed): SESSION_BEGIN, SESSION_END, WORKSPACE_ENTER, ROLE_ACTIVITY, CONTEXT_HINT, L1_DESCRIPTOR, USER_FEEDBACK_SIMULATED, GAP, RESET and QUERY_SUGGESTION. No role is "programmer", "artist", "person", "profession" or arbitrary personal text.
- Deterministic fast context state transitions, TTLs, how to combine missing/contradictory descriptors, explicit evidence quality and conservative UNKNOWN on insufficient support.
- **Slow, bounded** graph/routine representation: proposed max 16 nodes, 32 edges, 16 transition summaries; count saturation, eviction, aging/decay, cross-mode separation, duplicate replay and reset rules. Exact sizes and number of supporting sessions needed must be specified up front; do not copy R2.2's 256/4 support thresholds.
- An always non-executable explanation/query report enumerating learned associations and suggesting a *candidate* workspace profile only after support, otherwise UNKNOWN/NONE. No proposed physical rename/move/actuation.
- File size/row count, strict parser bounds, malformed input abort/abstain behavior, and no-persistence semantics.
- Resource budgets initially proposed: L2 state <=8192B; process RSS <=8192KiB; median <=50,000ns/event; measured per-event p95 <=250,000ns; finite >=100,000 synthetic events. Exact benchmark preregistration/guest compiler and timing methodology must be committed before results.

**V0.1 must demonstrate engineering-reproducible *experience divergence* for A and B, but must not call it successful user-specific optimization.** It must also demonstrate identical responses for shared invalid/safety cases.

## 4. Corpus-first preflight and failure tests (learn from R2.3 failures)

Strict future build order:
1. Preregister feature/data rules, exact model state, independent expected observation/episode outcomes, support gates and decision semantics in an initial commit.
2. Commit deterministic synthetic generator and a **different-code-path independent validator** before model code. No need for large data; use tiny sequences for engineering and finite sessions for test. Verify post-exclusion counts and whether the *actual proposed engine* can reach enough support on each synthetic device history **before freezing the corpus**. Known-negative examples must include post-reset insufficient support and corrupted session IDs.
3. Commit all corpus identities and SHA256 manifest. If invalid after freeze, mark study INVALID and version a fresh corpus rather than repairing the exposed test data.
4. Implement pure, bounded C11 analyzer after fixture freeze; test with strict C11, NDEBUG, sanitizers, historical RC0 nonregression, no network/OS live observation.
5. In V0.1, report only known-answer engineering/state-divergence cases. **Do not score scientific heldout proposal utility yet**. That is future V0.2/V0.3 work requiring separate frozen protocol.
6. Keep draft PR unmerged until independent review and owner approval.

Required negative tests: unsupported/missing context; stale/invalid quality; timestamp/sequence regressions; resets near end; no eligible rows; unknown category; huge numeric fields/overflow; duplicate IDs; graph capacity/eviction/saturation; malicious-looking text fields; contradictory hints; mode mixing; historic L1 core action isolation; proposed shell tokens or file paths never executed nor logged as trusted.

## 5. Scientific individuality study — separate future version

**Same code, same initial state**, two A/B simulated work histories, same query: different suggestions expected *only if supported by evidence*. Independent truth must specify which suggestions help which synthetic tasks **before generator/scorer access to heldout**.

Proposed evaluation categories:
- Familiar session continuation and restoration (without storing private paths).
- Workflow transition (CODE_EDIT -> BUILD_TEST vs REFERENCES -> CANVAS -> EXPORT).
- New, mixed or changing habits (no permanent vocational label).
- Competing actions and ambiguous evidence (abstain / surface alternatives).
- Rejected suggestions, reversed preferences, and long periods of inactivity (decay/stop harassment).
- Common safety alerts, stale input, no permission (same BLOCKED/UNKNOWN on all histories).

Use three no-learning baselines for comparison:
1. Always SAME DEFAULT workspace and never personalize.
2. Fixed category-to-template mapping with **same event inputs** (no hidden profile label).
3. Strong short-recency recent-event heuristic, calibrated fairly using only the permitted calibration split.
Optionally compare supervised static workspace templates if the memory candidate uses training feedback; disclose asymmetric labels. No superiority claims against the weakest baseline alone.

Freeze a utility metric before heldout: correct suggestions on *independent session episodes*, false/intrusive suggestions per 100 supported sessions, abstention/coverage, support after mode change, false reassurance on safety conflict, total effort proxy and undo burden. Require noninferiority on both A/B on harmful suggestions and a **preregistered strict gain** on an adequately populated task family against strongest baseline. Different outputs aren't sufficient; use independently derived, device-conditioned truth and maintain safety-identical probe behavior.

Training/calibration/untouched heldout must be disjoint by entire session/episode; hash-lock selected settings and source before reading heldout, no post-result tuning. Reject invalid corpus/harness and publish negative results. Since GitHub exposes test data, version/manifest timing is not proof no human saw the labels—state that limitation.

## 6. Permissioned OS adaptation research — not part of current scope

Even a successful simulated identity does not grant permission to edit files or change resource controls. Stage any future actions separately:
- Text-only proposal -> human review -> preview -> explicit approval with expiry and scope.
- Virtual organization overlay in a separately approved **guest-only test directory**, reversible mapping with deletion and stop controls; user can see what's proposed.
- Actual file move/rename requires a still later broker study with canonical scope, symlink/race/path-escape/collision safety, per-file rollback manifest and confirmed backups. Never assume a project build path is safe to relocate.
- Background task/scheduler/cgroup controls require their own rollback/nonregression study and authorization. No changes to Windows host, no direct L2->L1 policies, no L3 authority escalation.

Privacy threat model includes covert workplace surveillance, identity inference, linking opaque IDs across users, unbounded growth, replayed/injected activity hints, coercive persistent suggestions, stale approval, accidental exfiltration and mistaken consent. Deny by default.
