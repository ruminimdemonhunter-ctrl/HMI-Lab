## Transparent replay implementation

l1_inspect supports three finite operations:

    ./l1_inspect demo [CASE_NAME] [--details MAX_ROWS]
    ./l1_inspect trace ABSOLUTE_GUEST_PATH \
      [--forecast-config live-default|v06-trained] [--details MAX_ROWS]
    ./l1_inspect help

Every published and fixed comparison action is returned by an independent
l1_step_at() core. Shadow output is returned by l1_shadow_step_at() and never
feeds either action core. A third observer-off reference core receives the same
policy event, observation, and timestamp; its complete L1Core bytes and action
are compared after every row.

Explanations use actual observation, policy, candidate, confirmation, action,
fallback, and shadow state. Threshold hits are labeled descriptive conditions,
not a recreated decision algorithm. Pending/evaluated/unavailable shadow status
is separate from the published action.

Private V1 trace mode:

- accepts only bounded absolute paths without parent components;
- rejects non-regular files and every existing parser-negative condition;
- completes a checksum-validation pass before replay;
- buffers at most 2,000 detail records;
- checks device, inode, size, modification time, count, bytes, and checksum
  again before printing buffered results; and
- never prints the caller's private path.

The two-pass identity check reduces accidental and ordinary replacement races.
It is not authentication or a defense against a privileged adversary; V1 FNV-1a
remains corruption detection only.

## Maximum-row resource result

The preregistered optimized benchmark used a generated 86,400-row V1 trace,
five repetitions, no sleep, and no real PSI. The temporary trace stayed in
/tmp and was removed. Its exact V1 checksum was 44084e4b9d6b7a83.

Values are median (minimum..maximum), process CPU nanoseconds per row:

| Phase | Result |
|---|---:|
| strict streaming parser pass | 905.042 (650.019..1,024.442) |
| incremental core plus shadow over parser | 58.750 (0.000..224.807) |
| incremental bounded formatting over parser | 690.072 (338.699..947.434) |
| complete parser plus replay pass | 825.416 (657.317..1,129.848) |
| complete two-pass CLI process CPU | 3,626.701 (3,021.481..3,953.819) |
| complete two-pass CLI wall time per row | 3,633.656 (3,026.725..3,971.413) |

Complete optimized CLI RSS was 1,676 KiB median, range 1,600..1,708 KiB,
against the frozen 8,192 KiB limit: PASS. Benchmark-process RSS was 1,412 KiB.

Core/shadow and formatting values are paired incremental differences from
separate streaming passes. At this timescale scheduler and parser noise can
make a difference negative; the tool conservatively floors it at zero. The
complete pass and CLI measurements are directly measured and are the reliable
end-to-end quantities. CPU time is only an energy-cost proxy. No controlled
actuation or externally grounded counterfactual exists, so net savings and
energy benefit remain NOT_ESTABLISHED.

Sanitizer smoke RSS reached 18,916 KiB and is excluded from the optimized RSS
gate exactly as preregistered. Sanitizer passes are correctness evidence.

## Development discrepancies

Four implementation/validation-time failures were retained:

1. The first resource script assumed /usr/bin/time, which is absent in the
   guest. It was replaced with bounded fork/exec plus wait4 accounting in the
   C benchmark, eliminating that undeclared dependency.
2. The first five-repetition benchmark aggregated parser passes but executed
   the complete CLI only once. It was corrected before this report so every
   phase and complete CLI run has five independent observations and a
   median/range.
3. Two initial Windows-to-guest SSH commands passed the remote shell program as
   one quoted path. Both stopped before entering the project and ran no test;
   subsequent validation used argument-safe `make -C` invocations.
4. An initial normal and NDEBUG validation pair was launched concurrently in
   the same guest tree. The NDEBUG clean removed/replaced binaries while the
   normal argument suite was running, causing that normal run to fail. Both
   suites were then run sequentially from clean builds and passed completely.

None of these failures changed demo inputs, golden actions, checksums, the
core, the shadow learner, historical evaluation data, or scientific criteria.

## Limitations and human gate

- Demonstrations are small synthetic examples designed for inspection, not a
  held-out efficacy experiment.
- The fixed and risk-aware controllers agree on these short examples; no
  adaptive advantage is demonstrated.
- A shadow prediction is not a decision and remains ineligible for coupling.
- Optional private trace replay has no latent event truth and cannot measure
  causal resource savings.
- No research-length trace was recorded or uploaded in V0.9.
- FNV-1a and file metadata checks are not authentication.
- Formatted terminal throughput is not an intelligence-performance metric.
- No Windows host change, resource actuator, L2/L3 component, scheduler/cgroup
  write, kernel/device/firmware access, or hardware control was added.

The engineering candidate is ready for the architect to inspect using
docs/L1-human-acceptance.md. Personal acceptance remains a separate human gate;
it cannot convert the historical scientific NO-GO findings into GO.
