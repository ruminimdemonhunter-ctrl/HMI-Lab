Issue: [#3](https://github.com/ruminimdemonhunter-ctrl/HMI-Lab/issues/3)  
Protocol: [L1-v0.4-evaluation-plan.md](L1-v0.4-evaluation-plan.md)  
Implementation freeze: 04ff633  
Guest: Debian Linux 6.12.113+deb13-amd64, x86-64, GCC 14.2.0

## Outcome

**NO-GO for resource-actuation work.** The tuned fixed policy beat bounded
adaptation on the preregistered held-out loss (6380.50 versus 6731.00).
Adaptation also failed the independent memory guardrail: memory missed samples
increased from 190 to 205, and maximum detection delay increased from one to
three samples. No visible event was completely undetected, and all 504
invalid/regressing inputs per controller produced HOLD (zero fallback
violations).

This is an unfavorable result for the present debounce heuristic. It does not
show real workload optimization, learning, generalized intelligence, or
permission to control resources.

- Development: 20 scenarios, checksum a2336c7fdbef3be7.

The CPU differences are measurement noise, not evidence that adaptation is
faster. Timing includes controller initialization and scoring but excludes trace
generation. RSS is process-wide and includes all stored traces and metrics, so

## Final review coverage

The final PR correction makes held-out mode reject every policy except the
frozen training selection. It checks the exact six policy fields and their
deterministic 64-bit fingerprint (5147f61840da7089) before generating or
scoring held-out traces. The negative CLI test supplies a different but
otherwise valid policy and confirms rejection.

The sanitizer GitHub Actions job now runs make evaluation-ci using the existing
ASan/UBSan instrumented evaluator after make sanitize. This adds a complete
development, training, and one-repetition held-out smoke path under sanitizers.
The frozen seeds, generator, loss, core adaptation, held-out checksum, metrics,
and NO-GO conclusion did not change. Only timing and RSS may vary between smoke
runs and the recorded 100-repetition measurement.

In the final Debian rerun, the sanitizer smoke reported 19,856 KiB peak RSS and
CPU costs of 195.910/162.680/135.484 ns per decision for
default/fixed/adaptive. The optimized one-repetition smoke reported 4,212 KiB
and 32.116/31.566/26.250 ns. These differ from the recorded 100-repetition
measurement because sanitizer instrumentation, process startup, run length, and
guest load affect cost measurements; all decision metrics were identical.

The FNV-based fingerprint is a deterministic experiment-identity check, not a
cryptographic signature or policy authentication mechanism. Exact field
comparisons are also required, so fingerprint collision resistance is not
relied upon for the held-out gate.

## Validation and safety

- Normal, -DNDEBUG, ASan/UBSan/leak, state persistence/recovery, synthetic
  pressure trace, replay, and argument-bound tests passed in Debian.
- The evaluator produced zero non-HOLD responses on invalid observations or
  regressing timestamps.
- Source inspection found no evaluator calls to /proc, /sys, cgroups,
  schedulers, devices, sockets, subprocesses, or resource-control interfaces.
- The only evaluator write is the explicitly named training policy artifact.
  L1 remains recommendation-only; no L2/L3, service, actuator, kernel/device
  access, or hardware write was added.

## Limitations

- Scenarios and oracle labels are synthetic and hand-designed; five held-out
  seeds do not establish external validity.
- Samples within traces are correlated, and no confidence interval was
  preregistered.
- The oracle uses the same priority ordering as the compiled core and does not
  measure application latency, throughput, energy, or actual resource safety.
- Search considered only 108 policy points and one existing adaptation rule.
- CPU time is a short microbenchmark on one virtual CPU environment. RSS has
  process/page granularity. Neither is a whole-system overhead measurement.
- A deterministic replay can reveal regressions in declared scenarios but
  cannot demonstrate learning or generalization to real workloads.
