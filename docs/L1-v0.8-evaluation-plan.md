## Questions and immutable boundaries

V0.8 asks two independent questions:

1. Can a bounded recorder reduce process CPU cost below a preregistered budget
   while producing the same strict V1 trace values and preserving publication
   safety?
2. Is a separately authorized real PSI recording long and complete enough for
   the already frozen V0.7 observational forecast diagnostics?

The recorder remains an explicitly invoked, foreground, unprivileged Debian
program. It reads only CPU `some`, memory `full`, and I/O `full` from
`/proc/pressure/*`. It writes only a caller-selected trace and its
same-directory temporary name. It does not register PSI triggers, generate
load, run continuously, upload data, use the network, or change any scheduler,
cgroup, kernel, device, firmware, or hardware control.

The following remain byte/behavior compatible with merged V0.7:

- `HMI_L1_PSI_TRACE_V1`, its headers, rows, flags, FNV-1a definition, and
  parser limits;
- mode-0600 temporary creation, complete footer and file `fsync`, atomic
  no-replace publication, interruption cleanup, and destination-race safety;
- `--samples 2..86400`, `--duration-sec 2..86400`, cadence
  `1000..60000` ms, 16,777,216-byte file cap, 512-byte line cap, and the
  duration/cadence row-count rejection;
- all published L1 decisions, 104-byte `L1Core`, at-most-208-byte `L1Shadow`,
  and the 72-byte V2 persistent state plus V1 migration.

No raw real trace is committed or uploaded. The trace schema continues to
exclude wall time, host/user/process identity, paths, commands, free text,
network metadata, and credentials.

## Frozen implementations and optimization candidate

The baseline is the production recorder and Linux PSI adapter at base commit
`441c3053`. Its sample path opens and closes each of the three procfs files for
every observation and parses with the existing strict functions.

There is exactly one V0.8 performance candidate:

- open the same three PSI files once, read-only and close-on-exec;
- retain only three fixed file descriptors and fixed-size stack buffers;
- rewind/read each descriptor for every sample and invoke parsing with exactly
  the same accepted values, rounding, categories, and failure behavior;
- close every descriptor on success, read failure, signal, or publication
  failure; and
- retain the merged V0.7 one-shot adapter unchanged as the baseline comparator.

There is no dynamic allocation in the sample path, unbounded buffer, batch
retention, asynchronous thread, cache of PSI values, skipped read, reduced
durability, changed cadence, or alternative checksum. No additional candidate
will be introduced based on benchmark results in this milestone.

## Correctness protocol

The baseline and candidate consume identical deterministic PSI fixtures. The
valid fixture corpus contains exact CPU `some`, memory `full`, and I/O `full`
lines spanning zero, ordinary, boundary, and 100.00-percent averages with
monotonic 64-bit totals. Negative fixtures cover empty files, absent category,
malformed and out-of-range averages, missing/malformed/overflowing totals,
truncated lines, extra-long lines, read failure, and descriptor invalidation.

For every valid fixture, baseline and candidate must return identical validity,
basis-point values, and cumulative counters. Deterministic recorder runs must
produce parser-valid traces with identical data rows and checksum when supplied
the same mock samples and timestamps. No timestamp may be lost, duplicated,
regressed, or silently capped. Invalid observations remain zero-valued with
`valid=0` and flag bit 0; cadence overrun remains flag bit 1.

Existing tests remain mandatory for malformed headers/rows/footer, checksum,
empty/partial/extra input, valid and invalid flag masks, counter reset boundary,
sample/duration limits, deadline-aware sleep, oversized input, signals, output
creation races, no-replace publication, cleanup, and parser caps. Injected
tests cover open/read/rewind/close failures. Failure-injection tests may use
test-only callbacks or descriptors and must not add a production fault or
arbitrary-path interface.

Published-action equivalence, full-`L1Core` equivalence, the V0.7 stream and
schedule identities, V0.6 held-out identity, and the persistent-state size and
migration contract are hard gates.

## Frozen timing and resource measurements

All budget decisions use optimized `-O2` strict-C11 binaries in the same
unprivileged Debian QEMU guest. Sanitizer measurements are correctness evidence
only. Environment output records kernel, architecture, compiler, guest load
average, and whether a run is cold or warm. No workload is generated.

Process CPU comes from user plus system CPU returned by `getrusage`; wall time
comes from `CLOCK_MONOTONIC`. Sleeping is included in wall time and naturally
excluded from process CPU except for scheduling syscall overhead. Peak process
RSS is Linux `ru_maxrss` in KiB. Measurements are separated as:

- setup: process entry, CLI validation, destination checks, open, stream setup,
  and headers before the first sample;
- sample loop: clocks, three PSI reads and parsing, row encoding, hashing,
  writes, and sleep syscalls, but not sleep wall time;
- publication: footer, flush, file `fsync`, close, hard-link publication, and
  temporary-name removal;
- end to end: setup plus loop plus publication;
- hot source: PSI read and parse only, measured separately for attribution.

Recorder instrumentation uses only phase-boundary timing calls, never one
timing syscall per sample. It reports raw nanoseconds, counts, validity, wall
time, bytes, checksum, and RSS. Derived per-sample values always state their
numerator and denominator. One-time setup/publication costs are not presented
as per-sample steady-state work without also reporting the raw fixed cost.

The frozen populations are 5, 65, and 180 samples, five repetitions each.
Candidate order alternates baseline/candidate then candidate/baseline; the
fifth repetition uses baseline/candidate. One unreported warm-up precedes each
hot-source implementation. Results report all five values, median, nearest-rank
p95, minimum, and maximum. The 180-sample median is the primary efficiency
measure. Cold process runs and warm hot-source runs are reported separately;
no outlier is discarded. Background-load observations are notes, not exclusion
criteria.

Because a 65- or 180-second real recording is research-length evidence, it is
not authorized by this protocol or the implementation request alone. Until a
user separately supplies a finite duration and guest-local output path:

- hot-source profiles may read `/proc/pressure/*` repeatedly without retaining
  observations;
- bounded 2-to-5-sample live recorder smoke tests may validate integration;
- the 5/65/180 end-to-end population uses deterministic mock PSI input and a
  synthetic monotonic clock in a benchmark-only executable, without cadence
  sleeping or publishing a real recording; and
- no research-length real PSI trace is created.

The mock benchmark exercises the production parser, row encoder, hash, bounded
file output, flush/sync/close, and no-replace publication path. Its output is
explicitly labeled synthetic and cannot establish real-workload forecast
evidence. CI uses one bounded repetition of 5 and 65 mock samples and treats
timing only as a smoke check, not a budget gate.

## Frozen budgets and decision rule

`RECORDER_EFFICIENCY_GO` requires all of the following:

1. median optimized end-to-end process CPU at 180 mock samples is at most
   1,000,000 ns per valid sample;
2. all five optimized 180-sample runs are valid and peak RSS is at most
   8,192 KiB;
3. every optimized size has five completed repetitions with no discarded run,
   and setup, loop, publication, total CPU, wall time, and hot-source timing are
   separately reported;
4. baseline/candidate fixture values and deterministic trace rows/checksums are
   identical, with all strict parser, publication, signal, failure, and cap
   tests passing;
5. trace bytes remain at most 16,777,216, lines at most 512 bytes, and rows at
   most 86,400 without silent loss or truncation;
6. normal, `NDEBUG`, ASan, UBSan, leak, replay, state migration, historical
   V0.4-V0.7 identity/evaluation, and action-equivalence tests pass; and
7. the source/Git audit finds no raw recording, binary, credential, VM/backup,
   actuator, privilege, trigger write, networking/upload, L2, or L3 interface.

Failure of any item is `RECORDER_EFFICIENCY_NO_GO`. Passing authorizes only use
of the read-only recorder in further evidence collection; it does not revise
`DIAGNOSTICS: NO_GO` or authorize learner/action coupling.

## Real PSI evidence track

Real evidence is opt-in and independent of the efficiency verdict. A later
authorized trace records its schema/checksum, byte and row counts, permissions,
exact user-selected finite duration/cadence and guest-local destination,
recorder commit, compiler/kernel, validity/rejection accounting, and whether a
workload was externally present. Raw data remains guest-local.

Analysis preserves the V0.7 temporal split: first 60% development, then a
65-second embargo, then the remaining evaluation segment. No evaluation data
or offline event truth enters runtime adaptation. At least 30 non-overlapping
evaluated 60-second forecast windows are preregistered as the minimum for an
informative aggregate observational comparison; each class also needs at least
five positive and five negative outcomes for its class metrics to be described
as minimally populated. These are evidence-coverage thresholds, not claims of
statistical generalization or causality.

`REAL_EVIDENCE_READY` requires a strict valid trace, provenance above, at least
30 evaluation windows, at least 80% eligible issued forecasts, complete reason
accounting, and no development/evaluation leakage. Otherwise the result is
`REAL_EVIDENCE_INSUFFICIENT`, with deficient counts stated. A five-sample trace
is only a format/integration test. PSI stall counters are observational proxies
and cannot demonstrate resource-management benefit.

No research-length capture starts unless the user separately authorizes both a
finite duration and a specific guest-local output path. The recommended future
location is `/home/lab/hmi/data/v08-authorized.l1trace`; it is not created by
this milestone without that authorization.
