# HMI Level 1 v0.6 frozen outcome-feedback protocol

Status: **frozen before candidate implementation and before any V0.6 held-out
execution**. Issue: [#7](https://github.com/ruminimdemonhunter-ctrl/HMI-Lab/issues/7).

Changes to the horizon, targets, eligibility rules, learner, scenario generator,
seeds, candidate spaces, metrics, safety checks, overhead limits, or decision
criteria after this commit invalidate the experiment and require a new named
protocol. Implementation-only corrections made before the first held-out run
must be disclosed. After that run, only reporting defects may be corrected
without a new experiment.

## Research question and stage gates

Can a tiny fixed-capacity learner improve forecasts of future observable Linux
PSI pressure by matching forecasts made at time `t` with cumulative PSI stall
counter changes measured only after `t + H`?

This asks about forecasting, not causal resource optimization. L1 performs no
actuation, so later PSI cannot show that a recommendation caused improvement.
V0.4 and V0.5 remain negative experiments for action adaptation.

Two decisions are separate:

1. **Shadow-prediction RESEARCH_GO or NO_GO** evaluates predictive benefit.
   A GO permits only further read-only research.
2. **Action-coupling NO_GO** is unconditional in V0.6. Shadow output cannot
   alter a published action. V0.5's known I/O latency regression remains
   explicitly unresolved and no predictor may conceal it.

## Observable target and causal ordering

Linux PSI exposes cumulative `total` stall time in microseconds. V0.6 reads CPU
`some`, memory `full`, and I/O `full`; system CPU `full` is not used. This follows
the [kernel PSI interface](https://docs.kernel.org/accounting/psi.html). The
existing `avg10` values and decision adapter remain available and unchanged.

The nominal cadence is 1,000 ms and the single forecast horizon `H` is 60,000
ms. Windows never overlap:

```text
sample at t: validate observation/counters -> freeze one three-class forecast
        | no mutation of that forecast and no new forecast window
sample at t+H: validate later counters -> derive outcomes -> score -> feedback
        | only now may evidence counters change; next window may start
```

For class `c`, with cumulative counter `C`, measured monotonic interval
`elapsed_us`, and `delta = C_end - C_start`:

`future_pressure_bp = floor(delta * 10000 / elapsed_us)`.

Multiplication is implemented without unsigned overflow. An outcome is positive
when its future-window pressure is at least:

| Class | PSI source | Positive threshold |
|---|---|---:|
| CPU | `/proc/pressure/cpu`, `some total` | 800 bp |
| memory | `/proc/pressure/memory`, `full total` | 40 bp |
| I/O | `/proc/pressure/io`, `full total` | 150 bp |

These are future stall-time proxies, not workload labels. `avg10` is an
overlapping exponential average and is used only as information available when
the forecast is frozen, never as the future outcome.

An endpoint is eligible only from 60,000 through 65,000 ms after its start.
Any intervening invalid sample, consecutive-sample gap over 5,000 ms, timestamp
regression, end counter below start, or class delta greater than elapsed wall
microseconds invalidates the entire three-class window. Counter wrap is not
accepted: because a legitimate 64-bit PSI counter cannot wrap within 65 seconds,
a decrease is treated as reset/reboot/corruption. Too-early samples leave the
forecast pending; a late sample discards it. Missing or discarded outcomes are
reported and never scored as right or wrong.

Time regression, impossible delta, or counter decrease also resets learner
offsets and accumulated adaptation evidence to neutral. Ordinary invalid data
or a gap discards the pending window but does not fabricate feedback. Saturating
counters prevent arithmetic rollover.

## Runtime data separation and shadow safety

Code and documentation use three distinct concepts:

- `L1Prediction`: a frozen, live-available forecast from current `avg10` data;
- `L1Feedback`: later PSI-counter outcomes and availability, with no latent
  truth or action-quality grade;
- evaluator oracle: independent synthetic latent events used only offline for
  action metrics and never passed into the predictor or feedback function.

The Linux adapter owns file and clock access. The shadow component receives
explicit observations, counters, and monotonic timestamps. It performs no
allocation, I/O, clock read, syscall, logging, or network access. Its return
value is a shadow forecast only. The existing `l1_step_at()` call and published
V0.5 action remain behavior-identical whether the predictor is absent, enabled,
invalid, learning, reset, or saturated.

V0.6 evidence is transient. The 72-byte V2 state encoding and V1-to-V2
migration are byte-for-byte unchanged; forecasts, outcomes, counters, pending
windows, offsets, and gates are not persisted.

## Fixed and outcome-aware predictors

All predictors issue one binary forecast per class at each eligible window
start. A binary Brier score is therefore identical to error rate, but is
reported under both names for clarity.

1. **Always-negative** predicts no future class pressure.
2. **Tuned static persistence** predicts positive when the current class
   `avg10` is at least a training-selected class threshold.
3. **Outcome-aware shadow** starts with the same selected thresholds and uses
   only its own later observable feedback to adjust three independent bounded
   threshold offsets.

The static threshold search is the Cartesian product of:

- CPU `{400, 800, 1200, 2000}` bp;
- memory `{20, 40, 75, 125}` bp;
- I/O `{75, 150, 300, 600}` bp.

There are 64 candidates. Training selects the lowest macro-average binary
Brier score across CPU, memory, and I/O. Ties use higher macro F1, fewer total
missed outcomes, fewer false alarms, then lexicographically lower CPU, memory,
and I/O thresholds. Development cannot select thresholds.

The learner has signed class offsets in `[-2,+2]`. One offset step is CPU 200
bp, memory 10 bp, or I/O 40 bp. The effective prediction threshold is the
selected static threshold plus the saturated signed offset step and clamps to
`[1,10000]` bp.

For each evaluated window and class, saturated 16-bit false-alarm and miss
counters record only the learner's frozen forecast versus the later observable
outcome. Correct predictions do not act as errors. An adaptation gate requires
all of:

- at least 600 valid samples since gate/reset;
- at least 600,000 monotonic milliseconds since gate/reset;
- at least eight evaluated non-overlapping windows for that class.

At a gate, `misses >= false_alarms + 2` lowers that class threshold by one
offset step; `false_alarms >= misses + 2` raises it by one; otherwise it is
unchanged. An offset changes by at most one per gate and saturates at `[-2,+2]`.
Class evidence then resets. Classes gate independently. No outcome, latent
truth, decision switch, or future sample can update an offset early.

Initialization, explicit reset, timestamp regression, counter reset, or
impossible delta returns all offsets and adaptation evidence to neutral and
discards the pending forecast. Invalid or late windows increment bounded
missing-feedback accounting and are not adaptation evidence.

## Decision candidates and unchanged-action check

Forecast evaluation is independent of action evaluation. On identical
observations and timestamps, the evaluator runs:

1. frozen default L1, adaptation disabled;
2. a newly training-tuned fixed L1, adaptation disabled;
3. V0.5 risk-aware L1, unchanged;
4. V0.5 risk-aware L1 plus the V0.6 shadow component.

The action-policy search remains the V0.5 108-point space and loss:

`FP*1 + missed_CPU*4 + missed_IO*6 + missed_memory*10 + switches*0.25`.

Ties retain the V0.5 priority: memory misses/undetected, I/O
misses/undetected, CPU misses/undetected, false positives, switches, then
confirmation, CPU threshold, memory threshold, and I/O threshold.

Candidates 3 and 4 must publish exactly the same action at every sample and
finish with identical V0.5 core state. Any mismatch is a hard evaluator and CI
failure. V0.5 I/O regressions versus tuned fixed are reported, not reclassified.

## Deterministic generator

The evaluator uses PCG-XSH-RR32 and SplitMix64 with separate latent-event,
observation-noise, outcome-noise, and timing streams derived from each seed and
family. Integer arithmetic is normative. No platform randomness, live PSI,
clock, held-out output, or oracle feedback enters a runtime candidate.

Each sample contains independent latent event flags, noisy `avg10` observation,
cumulative outcome counters, validity, and explicit monotonic time. Counter
increments derive from the interval's latent stall rates plus independently
seeded bounded outcome noise, never from a predictor or action. Increments use
integer microseconds and saturate in generation rather than wrap. The evaluator
oracle applies the immutable action priority memory > I/O > CPU > HOLD.

Regular cadence is 1,000 ms. Baseline latent stall rates are CPU 100 bp, memory
2 bp, and I/O 10 bp. Positive regimes use CPU 1,800 bp, memory 120 bp, and I/O
450 bp. Noisy `avg10` observations lag transitions by a deterministic 10-sample
first-order integer filter before independent noise of CPU `[-300,+300]`,
memory `[-20,+20]`, and I/O `[-80,+80]`, clamped to `0..10000`. Family-specific
false spikes affect observations but not latent outcome counters.

## Fresh scenario families

Every seed produces all twelve families:

| ID | Family | Samples | Frozen purpose |
|---:|---|---:|---|
| 0 | idle | 1,800 | class imbalance, ordinary noise, no positive outcome |
| 1 | short-observation-noise | 1,800 | 1..8-sample false `avg10` spikes, no latent pressure |
| 2 | imminent-CPU | 2,400 | six CPU events with 30-sample pre-event ramps and quiet gaps |
| 3 | memory-urgency | 2,400 | short and sustained memory events, including transitions from CPU/I/O |
| 4 | I/O-urgency | 2,400 | short and sustained I/O events, including transitions from CPU |
| 5 | simultaneous-priorities | 2,600 | overlapping CPU/I/O/memory events and priority handoffs |
| 6 | regime-shifts | 3,600 | low/high/low base rates; forecasts must adapt then recover |
| 7 | delayed-inconsistent-outcomes | 3,000 | high current average before quiet and low average before future pressure |
| 8 | invalid-and-gaps | 2,400 | invalid blocks and timestamp gaps before and during pending windows |
| 9 | counter-reset-corruption | 2,400 | counter decreases and impossible interval deltas; evidence must reset |
| 10 | irregular-regressing-time | 2,400 | 250..2,500-ms cadence, late windows, and two timestamp regressions |
| 11 | long-drift-calibration | 4,800 | repeated nonstationary class regimes; multiple bounded gates |

Truth start/duration jitter and every family-specific interval are fixed in the
committed generator before training and held-out execution. The generator's
development, training, and held-out checksums are pinned in source/tests before
held-out mode becomes usable.

## Forecast metrics and uncertainty

For each predictor, class, family, and aggregate, report:

- eligible forecasts, evaluated outcomes, and missing/discarded feedback by
  reason (invalid, gap/late, regression, reset/decrease, impossible delta);
- TP, TN, FP, FN, precision, recall, specificity, false-alarm rate, F1, binary
  Brier/error rate, and positive outcome prevalence;
- lead time from a positive forecast window start to first latent event in the
  window, reported mean/nearest-rank p95/max for offline interpretation only;
- positive and negative forecast calibration (observed positive fraction for
  each binary forecast group);
- learner update count, offsets and min/max ranges, saturation/reset count;
- per-scenario macro Brier and paired learner-minus-static differences.

Undefined ratios are printed as unavailable rather than zero. Aggregate values
are micro-summed. Uncertainty uses whole scenarios: report mean, sample standard
deviation, median, minimum, and maximum paired macro-Brier difference; the
fraction of scenarios favoring the learner; and an exact two-sided paired sign
test excluding ties. Correlated samples are not treated as independent trials.

## Action, safety, and overhead metrics

For each action controller/family and aggregate, retain V0.5 metrics: weighted
loss, FP, class misses and undetected events, detection delay mean/p95/max,
switches, adaptation events/ranges, invalid/regressing fallback violations,
process CPU ns/decision, `sizeof(L1Core)`, RSS, and 72-byte state size.

Memory and I/O visible events are paired against tuned fixed on identical
traces. Report equal/faster/slower entry, worst added delay, per-class misses,
undetected events, p95, and max. V0.6 shadow must add exactly zero action/state
differences versus V0.5; it is not allowed to repair V0.5 actions.

Budget limits for the optimized Debian build are:

- `sizeof(L1Shadow)` at most 512 bytes and no dynamic hot-path allocation;
- shadow update CPU median at most 250 ns/sample over five 10-million-sample
  core repetitions;
- combined observation-plus-shadow median CPU overhead no more than 10% or
  25,000 ns/sample, whichever absolute allowance is larger, versus V0.5
  observation-to-decision on identical live samples;
- evaluator peak RSS below 16,384 KiB; state file exactly 72 bytes.

Timing order rotates by repetition. RSS is process-wide and not attributed to
one controller. Live benchmarks are guest-load sensitive and do not measure
workload benefit.

## Scientific decisions

Shadow-prediction **RESEARCH_GO** requires all of:

1. zero action mismatches and zero invalid/regressing fallback violations;
2. valid counters/offsets remain inside compiled bounds and V2 bytes remain
   unchanged;
3. aggregate learner macro Brier at least 5% relatively lower than tuned
   static persistence;
4. learner Brier no worse for any class and learner recall no lower by more
   than 0.02 absolute for any class;
5. learner improves whole-scenario macro Brier in at least 60% of non-tied
   scenarios and the exact paired sign-test two-sided `p <= 0.05`;
6. the improvement occurs for at least four of five held-out seed aggregates;
7. missing-feedback rate and every discard reason are reported, with at least
   80% of issued windows evaluated;
8. all CPU, memory, RSS, storage, and fixed-capacity budgets pass.

Failure of any condition is **NO_GO** and unfavorable class outcomes are
reported explicitly. Regardless of forecast outcome, action coupling remains
**NO_GO**. Existing V0.5 memory and I/O comparisons are reported independently;
they cannot be claimed as shadow-predictor effects.

## Reproducibility and required validation

Training writes a strict manifest containing protocol ID, split checksums,
candidate counts, selected action policy, selected static forecast thresholds,
training metrics, and deterministic fingerprints. Held-out mode verifies every
frozen identity before generating held-out traces. The manifest is an
experiment identity check, not authentication.

Planned Debian commands are:

```bash
cd /home/lab/hmi/src/level1
make clean all test
make test-ndebug
ASAN_OPTIONS=detect_leaks=1 UBSAN_OPTIONS=halt_on_error=1 make sanitize
make evaluation-v06-development
make evaluation-v06-train
make evaluation-v06-heldout EVAL_REPETITIONS=100
make evaluation-v06-ci
make bench replay shadow-bench
```

GitHub Actions runs normal, `NDEBUG`, historical replay/evaluations, bounded
V0.6 evaluation, ASan/UBSan/leak checks, and a sanitizer-backed V0.6 held-out
smoke test. Final results record exact commands, checksums, compiler/guest,
errors, negative results, and limitations.

The experiment is unprivileged and read-only. It adds no L2/L3, actuator,
scheduler/cgroup/kernel/device/firmware interface, network updater, privileged
operation, or host write. A successful result permits further read-only
research only.
